# Архитектура STEALTHNET на Rust

## Опорные решения

- Remnawave 3.4.11 — источник истины по VPN: пользователь, срок, статус, трафик, устройства, ноды, сквады, хосты. Хосты (названия серверов в приложении, адреса, порядок) у себя не храним: вкладка «Хосты» и блок сквада «Что видят клиенты» читают и меняют их прямо в Remnawave. У себя храним ссылку на пользователя (числовой `id`, `shortUuid`) и зеркало для списков и лент. Решения о доступе принимаем по свежему ответу Remnawave.
- Деньги живут только в нашей базе: заказы, платежи, журнал баланса. Суммы — целые минорные единицы, без `float` и `numeric`.
- Валюта у установки одна: доллары по умолчанию или рубли. У звёзд Telegram своя цена в тарифе, курса нет.
- Тарифы и категории создаёт оператор. Код опирается только на свойства тарифа: категория, сроки, цены, устройства, лимит и сброс трафика, сквады.
- Оплата и выдача разделены. Вебхук в одной транзакции отмечает платёж и ставит задачу выдачи; воркер применяет заказ к Remnawave, повторяя при сбоях.

## Крейты и границы

```
sn-domain ← sn-remnawave
          ← sn-store
          ← sn-payments
          ← sn-modules (+ sn-store, axum)
          ← sn-services (+ все выше)
                ← sn-server, sn-worker, sn-bot
                        ← sn-app
```

| Крейт | Отвечает за | Не делает |
|---|---|---|
| `sn-domain` | Типы и правила: `Money`, `Stars`, `Tariff`, `quote`, `plan`, статусы заказа и платежа, `DomainEvent`, `ModuleId` и каталог | Ввод-вывод, время берёт аргументом |
| `sn-remnawave` | `RemnawaveApi` (типаж), `RemnawaveClient` (HTTP), модели, `webhook` (подпись, разбор, удаление секретов), `fake::FakeRemnawave` для тестов | Знает о наших заказах |
| `sn-store` | `Store`, `Db` (общий для соединения и транзакции), репозитории, миграции, `SecretBox` | Бизнес-решения: принимает готовые данные и проверяет переходы статусов |
| `sn-payments` | `PaymentProvider`, `ProviderRegistry`, провайдеры | Ходит в базу |
| `sn-modules` | `Module`, `ModuleRegistry`, `CoreApi` (что ядро даёт модулям), закрытие маршрутов выключенного модуля | Ходит в Remnawave |
| `sn-services` | `Services` и сценарии: `auth`, `clients`, `checkout`, `inbox`, `fulfillment`, `subscriptions`, `remna_sync`, `autorenew`, `events`, `stars_review`, `legacy` (перенос из другого бота) | HTTP |
| `sn-server` | Маршруты, извлечение сессий, перевод ошибок в HTTP | Бизнес-логика: только вызов сценариев |
| `sn-worker` | Очередь `jobs` (`FOR UPDATE SKIP LOCKED`, аренда с токеном, повторы), рассылка событий модулям, периодические работы: обслуживание, автопродление, сверка, досверка выдачи, завершение давно истёкших подписок | — |
| `sn-bot` | Long polling, экраны, оплата звёздами через `inbox().stars_*` с журналом `bot_star_events` и сверкой `getStarTransactions` | Свои правила цены и выдачи |
| `sn-app` | Конфиг из окружения, логи, команды `serve`, `migrate`, `create-admin`, `gen-secret-key`, `import-legacy` | — |

Публичные типы `sn-domain` и типажи `RemnawaveApi`, `PaymentProvider`, `Module`, `CoreApi` — контракт для всех крейтов. Менять их можно только добавлением, без переименований.

## Ядро и модули

Ядро работает всегда: клиенты и подписки, тарифы и пробный период, платежи и автопродление, поддержка, ноды, сквады и хосты, бот, кабинет и мини-приложение, настройки и доступы.

Модуль — реализация `sn_modules::Module` с одним из 23 `ModuleId` из каталога (`sn_domain::module::CATALOG`, данные из макета «Модули»). Пока модуль не написан, на его месте `Placeholder`: в админке он виден и переключается, но ничего не делает.

Что модуль может:

- отдать маршруты админки и клиента: они монтируются на `/api/admin/m/{id}/…` и `/api/client/m/{id}/…`, вход проверяет сервер, а выключенный модуль отвечает 404 `module.disabled` без перезапуска. Сервер кладёт в расширения запроса клиента его адрес (`sn_modules::catalog::web::ClientAddr`), посчитанный по тем же правилам доверенных прокси, что и для лимитов входа;
- поправить цену: `quote_adjustments` возвращает скидки, их применяет `sn_domain::pricing::quote`. Хуки цены (`quote_adjustments`, `quote_item`) ядро вызывает, уже отпустив своё соединение с базой: модуль берёт соединение сам, и расчёты не исчерпывают пул;
- участвовать в заказе: `on_order_created`, `on_order_paid`, `on_order_canceled` вызываются в транзакции ядра. Отказ (`ModuleError::Invalid`) при создании отменяет оформление, при оплате отправляет заказ на ручную проверку без выдачи;
- реагировать на события ядра: `on_event` получает `DomainEvent` из таблицы `domain_events` (outbox), воркер раздаёт их каждые 2 секунды. Получатели — модули, включённые при первой раздаче. После ошибки модуля событие повторяется: пауза 5 с, удваивается до часа, всего 12 попыток (около 3,4 ч), затем доставка уходит на ручную проверку (`event_deliveries`, аудит `module.event_review`). Пока у модуля висит более раннее событие клиента, следующие события этого клиента ему не отдаются. Выключенный модуль событие не держит. Разбор в админке: `GET /api/admin/events/review`, `POST /api/admin/events/{id}/retry`;
- работать по расписанию: `tasks` и `run_task`;
- добавить кнопки в бот: `bot_entries`;
- менять баланс, дни подписки и ставить задачи только через `CoreApi`;
- писать в бот: `CoreApi::bot_sender` отдаёт отправителя Bot API (`sn_modules::BotSender`). Его регистрирует `sn-app` (`sn_bot::broadcast::TelegramSender`), без него — `None`;
- писать на почту: `CoreApi::mail_sender` отдаёт `sn_modules::MailSender` поверх модуля «Почта» (`sn_services::mail::MailBridge`). `site()` говорит, готова ли почта и какой адрес сайта ставить в ссылки, `send()` отправляет письмо с HTML, текстом и заголовками отписки;
- отдать публичные маршруты без входа: `public_routes` монтируются на `/api/public/m/{id}/…`, выключенный модуль отвечает 404 `module.disabled`;
- выдать клиенту подписку без оплаты: `CoreApi::grant_subscription` в транзакции модуля создаёт заказ `module_grant` и задачу выдачи, `CoreApi::grant_preview` заранее говорит, что получится (новая подписка, продление или переход) и почему выдать нельзя; `CoreApi::notify_in` ставит уведомление в той же транзакции.

Чего модуль не делает: не вызывает Remnawave сам и не пишет в `client_balances` напрямую. Свои таблицы модуль создаёт своей миграцией в общей последовательности, поэтому таблицы выключенного модуля существуют и данные не теряются.

Как подключить модуль:

1. Реализовать `Module` в `sn-modules/src/catalog/<id>.rs` (или в отдельном крейте `sn-mod-<id>`).
2. Передать экземпляр в `ModuleRegistry::new(vec![…])` в `sn-app`.
3. Если нужны таблицы — миграция `crates/sn-store/migrations/<номер>_<id>.sql`.
4. Настройки описать через `settings_schema`: форма в админке строится по схеме, секреты хранятся зашифрованными.

Модуль может быть доступен только в одной валюте (`only_currency`): реестр не даёт его включить и считает выключенным в другой валюте.

## Рассылки

Модуль `broadcast` (`sn-modules/src/catalog/broadcast/`), страница админки `/admin/m/broadcast`. Таблицы — миграции `0170_broadcasts.sql` и `0171_broadcast_email.sql`: `broadcasts` (текст в HTML-разметке Telegram, картинка, кнопки, аудитория, канал, тема письма, состояние), `broadcast_recipients` (очередь получателей по каналам), `broadcast_images` (картинки, код файла в Telegram и публичный ключ для писем), `broadcast_unsubscribes` (отписавшиеся адреса).

- Канал рассылки (`channel`): `bot`, `email` или `both`. При `both` каждый клиент получает рассылку в каждый канал, где с ним есть связь: в бот — если есть Telegram и бот не остановлен, на почту — если есть адрес в `client_identities` (подтверждённый или нет) и он не отписался. В очереди у каждой строки свой канал, ключ строки — `(broadcast_id, channel, client_id)`, один адрес получает одно письмо на рассылку. Тема письма обязательна для почты, до 150 знаков.
- Состояния: `draft` → `scheduled` (отмена возвращает в черновик) → `sending` → `done`; остановка во время отправки — `canceled`, оставшиеся получатели помечаются `skipped`. Править можно только черновик.
- Аудитория: все клиенты, активные (без пробных), заканчивается в течение N дней, закончилась (была подписка, сейчас нет), не подключались, пробный период, ни разу не было подписки, тариф. Подписка клиента берётся та же, что в списке клиентов (`effective_status`, приоритет действующей). Клиенты удалённые и заблокированные не получают ничего, остановившие бота (`bot_unreachable`) — сообщений в бот, отписавшиеся — писем. Подсчёт `POST /api/admin/m/broadcast/audience` показывает по каждому каналу, сколько получат и сколько исключено.
- Список получателей собирается одним `INSERT … SELECT` в момент старта (сразу или по расписанию), поэтому рассылка по расписанию берёт аудиторию на время отправки.
- В бот отправляет `broadcast::Engine`, запущенный рядом с воркером. Работает один отправитель на канал: аренда `broadcast.engine` в `bot_state` на 20 с с продлением. Темп — не больше 25 сообщений в секунду на всех и одно в секунду на чат, рассылки идут по очереди старта. Ответ 429 ставит на паузу всю отправку на `retry_after`, получатель возвращается в очередь без учёта попытки. 403 и «chat not found» — получатель `blocked`, клиенту ставится `bot_unreachable`. Сбой сети и 5xx — до 3 попыток с паузой, потом `failed`. Десять отказов Telegram подряд без единой доставки останавливают рассылку с причиной.
- Письма отправляет второй `broadcast::Engine` со своей арендой `broadcast.mail` (`EngineConfig::mail`): 2 письма в секунду, не больше двух в полёте, рассылки по очереди старта, бот и почта идут одновременно. Отказ адреса (SMTP 5xx на получателя, Resend 422 про `to`) — строка `failed` с ответом сервера. В итогах причины складываются без самого адреса (он заменяется на `<адрес>`), а адреса с ответом сервера идут списком `failed_emails`, до 100. Resend 429 — пауза на `retry-after`, письмо возвращается в очередь без учёта попытки. Почта выключена, не настроена, не принимает ключ или пароль, нет связи — пауза 60 с, причина в `mail_notice`, очередь ждёт, пока почта заработает. Временный сбой — до 3 попыток. Рассылка заканчивается, когда пусты очереди всех её каналов.
- Письмо (`letter.rs`) собирается из того же HTML Telegram: переносы становятся `<br>`, премиум-эмодзи — обычными, у ссылок, кода и цитат — встроенные стили; текстовая часть — без тегов, адрес ссылки в скобках. Кнопки — ссылки, раздел бота ведёт на страницу кабинета. Картинка — по ссылке `/api/public/m/broadcast/images/{public_key}`. Для писем нужен адрес сайта (`core.public_url`), без него почтовый канал недоступен.
- Отписка: у почтовой строки свой токен `unsubscribe`. В письме ссылка «Отписаться от рассылок» на `/api/public/m/broadcast/unsubscribe/{token}` и заголовки `List-Unsubscribe` и `List-Unsubscribe-Post: List-Unsubscribe=One-Click`. `GET` показывает страницу с кнопкой, `POST` отписывает адрес (так же работает кнопка почтовой программы), `POST …/resubscribe/{token}` возвращает подписку. Аудит `broadcast.unsubscribed` и `broadcast.resubscribed` от имени клиента.
- Перезапуск: получатель забирается из очереди отдельным коммитом (`state = 'sending'`) прямо перед отправкой. При штатной остановке отправка дожидается ответов Telegram и почты и записывает их. Каждый отправитель разбирает только строки своего канала. После аварии такие строки новый отправитель помечает `failed` с причиной «дошло ли — неизвестно» и не повторяет, остальная очередь продолжается: дублей нет, очередь не теряется.
- Картинка грузится в Telegram файлом один раз, дальше идёт по `file_id` (привязан к боту). Устаревший код — повторная загрузка.
- Кнопки: ссылка или раздел бота. Раздел передаётся как `n:<код раздела>`: бот открывает экран новым сообщением, сама рассылка остаётся в чате.
- Проверка на одном клиенте в бот или письмом на указанный адрес — `POST /api/admin/m/broadcast/test`, отправка сразу, без очереди; ссылка отписки в проверочном письме никого не отписывает. Всё под правом `marketing`, действия пишутся в аудит (`broadcast.started`, `broadcast.scheduled`, `broadcast.unscheduled`, `broadcast.canceled`, `broadcast.test`).

### Автоматические рассылки

Правило — событие, срок в днях, сообщение и канал как у разовой рассылки, включено или выключено. Таблицы — миграция `0200_auto_broadcasts.sql`: `auto_broadcasts` (правила, удаление мягкое), `auto_broadcast_cases` (журнал случаев, ключ `(rule_id, case_key)`), у `broadcasts` поля `rule_id`, `rule_day`, `rule_version`. Код — `broadcast/auto.rs` и `auto_store.rs`, страница `/admin/m/broadcast/auto`.

- События и условия (по подпискам и покупкам клиента, не по тарифам), момент срабатывания и ключ случая:
  - `expiring` — подписка действует (не `disabled`, не завершена, есть в Remnawave), до `expire_at` осталось N дней (N ≥ 1); пробные тоже; с автопродлением — только если оператор отметил «писать и им». Ключ — подписка и час окончания: продление даёт новый случай.
  - `expired` — подписка (не пробная) закончилась N дней назад, срок с тех пор не продлён, другой действующей подписки нет, подписка не отключена и не завершена раньше срока. Ключ — подписка и час окончания.
  - `trial_ended` — пробная подписка закончилась N дней назад (N может быть 0), покупок нет, другой действующей подписки нет.
  - `no_purchase` — клиент зарегистрирован N дней назад, покупок нет; перенесённые (`import`, `migration`) не считаются. Ключ — клиент.
  - `not_connected` — с первой оплаты подписки прошло N дней, подписка действует, `first_connected_at` пуст. Ключ — подписка.
  - Покупка — заказ `new`, `renewal` или `change` с `paid_at`, или подписка вида `paid`. Пробный период и выдача админом покупкой не считаются.
- Проверка — задача модуля `auto` раз в 5 минут (`ScheduledTask`, воркер). Случаи, у которых срок ещё не наступил, не трогаются. Догоняются случаи за последние 24 часа: после простоя, включения или создания правила старые события не рассылаются.
- Правило проверяется в транзакции под `FOR UPDATE` строки правила, по 500 случаев за раз. Случай пишется в журнал в той же транзакции, что и получатели: каждый случай — одно сообщение, без повторов после перезапуска и при двух воркерах.
- Отправляет тот же `broadcast::Engine`: правило складывает получателей в скрытую пачку — строку `broadcasts` на правило, день и версию текста (`rule_day`, `rule_version`, уникальный индекс `broadcasts_rule_day_key`). Темп, 429, остановленный бот, отписка, ссылка отписки в письме и повтор после аварии — как у разовых, общая очередь с разовыми рассылками. Пачки не видны в списке разовых и в их маршрутах. Правка текста, картинки, кнопок, канала или темы поднимает `version`, новые случаи идут новой пачкой. В одной пачке клиенту одно сообщение в канал: если у клиента в один день наступило два случая одного правила, второе сообщение не уходит.
- Без связи: нет Telegram или бот остановлен (`bot_unreachable`), нет почты или адрес отписался — случай записывается с `queued = false` и больше не повторяется. Почта не настроена: правило «на почту» не срабатывает и ждёт, «в бот и на почту» отправляет только в бот; причина — в `auto_broadcasts.notice`. Включить правило с почтой без настроенной почты нельзя.
- Выключение и удаление правила снимают из очереди его сообщения, которые ещё не ушли (`skipped`). Картинка правила не удаляется очисткой.
- Системные уведомления (оплата, выдача и продление, автопродление, ответы поддержки) идут сами по себе; правило их не заменяет и не повторяет без выбора оператора.
- API (право `marketing`): `GET|POST /api/admin/m/broadcast/auto`, `GET|PUT|DELETE /auto/{id}`, `POST /auto/{id}/switch {enabled}`, `POST /auto/reach {trigger, days, with_autorenew, id?}` — сколько случаев наступило за сутки и ещё не обработано, по каналам. Аудит: `broadcast.auto_created`, `broadcast.auto_updated`, `broadcast.auto_enabled`, `broadcast.auto_disabled`, `broadcast.auto_deleted`.

## Подарки и промо-ссылки

Модули `gifts` и `promolinks` (`sn-modules/src/catalog/gifts/`, `promolinks/`), таблицы — миграция `0210_gifts_promolinks.sql`: `gifts`, `promo_links`, `promo_link_activations`, у `orders.kind` новое значение `module_grant`.

Выдача модулем. `CoreApi::grant_subscription` (`sn-services/src/grants.rs`) под блокировкой клиента решает, куда идёт подписка, и в транзакции модуля создаёт бесплатный заказ `module_grant` с `PurchaseIntent::ModuleGrant` (модуль, ссылка на запись модуля, тариф и срок или свои параметры) и задачу выдачи. Дальше — обычная выдача (`fulfillment`): план, Remnawave, зеркало, событие, уведомление «подписка готова». Заказ `module_grant` не считается покупкой: оплатой клиента он не является ни в статистике, ни в авторассылках.

- Подписка по тарифу (подарок) ведёт себя как покупка того же тарифа без выбора подписки. Одна подписка на клиента: единственная живая подписка той же категории продлевается, другой категории — переход на тариф с заменой (оставшиеся дни не переносятся, получатель видит это до активации), пробная заменяется. Несколько подписок: пробная заменяется, иначе выдаётся новая; получатель может выбрать подписку той же категории для продления (`GrantTarget::Subscription`) или новую (`GrantTarget::New`). Новая подписка получает вид `gift`, автопродление у неё выключено.
- Своя подписка без тарифа (промо-ссылка): сквады, срок, трафик и устройства из ссылки, вид `promo`, `tariff_id` пустой. Одна подписка на клиента: если есть действующая подписка не пробная, выдача отказывает (`grant.has_subscription`), истёкшая или пробная заменяется. Несколько подписок: всегда новая. Если к моменту выдачи у клиента появилась действующая подписка, заказ уходит на ручную проверку, а не заменяет её.
- Отказы до создания заказа: клиент заблокирован, Remnawave не подключена, тарифа больше нет, у подписки нет сквадов, выбранная подписка не найдена. Модуль при отказе откатывает свою транзакцию, код или активация не тратятся.

Подарки:

- Покупка — товар модуля `gift` (`{tariff_id, period_id}`) через `/api/client/items/quote` и `/api/client/items/checkout`, в боте — раздел «Подарить подписку» (`x:gifts`, `gb`, `gt:…`, `gp:…`, `gy:…`). Работают все способы оплаты оформления, включая способы внутри платёжки и звёзды; промокоды к подаркам не применяются. Цена — цена срока тарифа. Дарить можно тарифы в продаже со сквадами; в настройках модуля (`GET/PUT /api/admin/m/gifts/settings`, хранятся в конфиге модуля) — все тарифы или только выбранные и срок действия кода в днях (по умолчанию 90, 0 — без срока).
- После оплаты выдача заказа вызывает `fulfill` модуля: один код на заказ (`gifts_order_key`), формат `XXXX-XXXX-XXXX` из 32 знаков без похожих символов, срок кода считается от выпуска. Дарителю в той же транзакции ставится уведомление `gift.ready` с кодом, ссылкой на бота `t.me/<бот>?start=gift_<код>` и ссылкой на кабинет `/cabinet/gifts?code=<код>`; без Telegram — письмо.
- Активация: бот по `/start gift_<код>` или по коду сообщением, кабинет и мини-приложение — `POST /api/client/m/gifts/preview` и `/redeem` (`code`, `subscription_id`, `new`). Код принимается без дефисов и в любом регистре. Строка подарка блокируется, заказ дарителя — `FOR SHARE`: если деньги вернули, код гасится (`canceled`), пока по оплате ждём возврат — активация откладывается. Код одноразовый; повтор тем же клиентом — «Вы уже активировали», другим — «уже активирован». Дарителю — уведомление `gift.redeemed` (себе — нет).
- Возврат: событие `payment_refunded` гасит неактивированный подарок, если заказ стал `refunded`; частичный возврат подарок не трогает. Возврат после активации подписку не отбирает — это решает администратор.
- Админка (право «Маркетинг»): `GET /api/admin/m/gifts/gifts?status=&q=&limit=&after=` — поиск по коду, тарифу, Telegram, нику, имени и почте дарителя или получателя; `GET /summary` — счётчики состояний.

Промо-ссылки:

- Ссылка (право «Маркетинг», `GET|POST /api/admin/m/promolinks/links`, `POST /links/{id}/switch`): название, код (4–32 знака, свой или случайный), сквады, срок в днях, трафик в ГБ (пусто — без лимита) и сброс, устройства (0 — не ограничивать), лимит активаций, дата окончания. Аудит `promolinks.created`, `promolinks.enabled`, `promolinks.disabled`.
- Клиент открывает `t.me/<бот>?start=pl_<код>` (можно вместе с UTM-метками через `__`) и сразу получает подписку. Одному клиенту — одна активация ссылки (`promo_link_activations_client_key`); лимит считается под блокировкой строки ссылки. Ответы бота на повторную, выключенную, просроченную, исчерпанную и несуществующую ссылку — тексты раздела «Промо-ссылки».
- Статистика: активаций и сколько из активировавших потом оплатили подписку (заказ `new`, `renewal` или `change` оплачен после активации и не отменён и не возвращён).

## Конкурсы и рулетка

Модули `contests` и `roulette` (`sn-modules/src/catalog/contests/`, `roulette/`), общий для них приз — `catalog/prize.rs`: дни подписки, деньги на баланс, личный промокод на скидку или «пусто» (только в рулетке). Таблицы — миграция `0230_contests_roulette.sql`.

Конкурсы, страница `/admin/m/contests`:

- Таблицы: `contests` (название, приз и число победителей, условия в `conditions`, сроки, зерно жеребьёвки и его отпечаток), `contest_entries` (участники, причина исключения, билет, место, выдача приза), `contest_messages` (напоминания и итоги), `contest_log` (журнал). У `broadcasts` поле `contest_message_id` — скрытая пачка сообщения конкурса.
- Условия — по данным проекта, не по названию тарифа: действующая подписка (можно без пробных), оплата подписки, продления или опций за период (заказы `new`, `renewal`, `change`, `module` с `paid_at`, кроме возвращённых и отменённых; можно с минимальной суммой), приглашённые за время конкурса друзья из `referral_links` (можно засчитывать только оплативших). Проверяются при вступлении и ещё раз на момент итогов: кто перестал подходить, исключается с причиной.
- Клиент вступает кнопкой «Участвовать» в боте (`cj:{id}`, экран `ct:{id}`, раздел `x:contests`, кнопка «Конкурсы» в меню, пока идёт хотя бы один конкурс). Вступление — в транзакции под `FOR SHARE` строки конкурса, жеребьёвка берёт её `FOR UPDATE`: после итогов вступить нельзя.
- Жеребьёвка честная и проверяемая: при создании выбирается случайное зерно (32 байта, `OsRng`), до итогов видно только `seed_hash` = sha256 от зерна в hex. На итогах для каждого участника считается sha256 от строки «зерно:номер клиента», побеждают наименьшие значения; зерно открывается, `list_hash` — sha256 номеров участников по возрастанию через перевод строки. Список с билетами — `GET /contests/{id}/entries.csv`.
- Задача модуля `run` раз в минуту: жеребьёвка наступивших конкурсов, выдача призов, постановка сообщений. Деньги и промокод выдаются в той же транзакции, что отметка о выдаче (ключ идемпотентности `contest:{id}:{client}`). Дни — через ядро после отметки `issuing`; нет живой подписки — приз ждёт (`waiting`) и выдаётся, когда подписка появится; сбой Remnawave — `failed`, повтор кнопкой «Выдать снова». Победитель получает личное уведомление (`contest_won`, `contest_waiting`).
- Напоминания и итоги отправляет `broadcast::Engine` через скрытые пачки: тем, кто не участвует (можно только подходящим по условиям), участникам, итоги — участникам без приза. Подстановки `{title}`, `{prize}`, `{winners}`, `{date}`. Время прошло больше чем на 12 часов или конкурс уже закончился — сообщение не уходит, причина в журнале. Отмена конкурса снимает неотправленное.
- Править можно до старта всё, во время конкурса — название, описание, сообщения и отложить итоги. Удалить — только не начавшийся. API (право `marketing`): `GET /options`, `GET|POST /contests`, `GET|PUT|DELETE /contests/{id}`, `POST /contests/{id}/cancel`, `GET /contests/{id}/entries`, `POST /contests/{id}/winners/{client}/retry`.
- Антибот (`antibot::guard`, настройка `contest_guard`, по умолчанию включена). Режим запрета: отмеченный клиент получает `JoinOutcome::Denied` до проверки условий, на жеребьёвке участник с открытой отметкой исключается с причиной `ANTIBOT_EXCLUDED` (клиенту показывается «Участие для этого аккаунта недоступно»), в `contest_log` — запись `antibot`, в журнал антибота — `contest_excluded`. Режим подтверждения: после проверки условий `JoinOutcome::Confirm`, бот показывает «Я не робот» с колбэком `cjr:{id}:{токен}`, `join_confirmed` проверяет кнопку и вступает. Режим отметки: вступление пишется в журнал (`contest_noted`). Друзей из `referral_links` проверяет `antibot::screen_invites`: самоприглашение (общий адрес или почта с пригласившим) и массовые приглашения не засчитываются ни в каком режиме и получают отметку, как при оплате приглашённого; отмеченные друзья не засчитываются в режиме запрета. Снятая вручную отметка возвращает обычные права сразу.

Рулетка, страница `/admin/m/roulette`, лента призов в мини-приложении `/app/roulette`:

- Настройки — одна строка `roulette_config` с версией: призы-карточки (приз, вес, своя подпись), бесплатное вращение раз в N дней (всем, с подпиской или только с оплаченной), вращение за покупку (можно от суммы), бюджет на период (сутки, 7 или 30 дней) по деньгам, дням и числу промокодов.
- Исход решает сервер: `POST /api/client/m/roulette/spin {request_id, subscription_id?}` под блокировкой клиента. Из розыгрыша исключаются призы, которые сейчас нельзя выдать: дни без живой подписки, промокод при выключенном модуле «Промокоды», приз сверх бюджета. Выбор — по весам из `OsRng`. Повтор с тем же `request_id` возвращает то же вращение.
- Вращение за покупку — строка `roulette_tickets` на оплаченный заказ (`on_order_paid`, ключ — заказ), возврат оплаты сжигает неиспользованное вращение. Бесплатное сначала, вращения за покупки копятся.
- `roulette_spins` хранит снимок приза: деньги и промокод выдаются в той же транзакции, дни — через ядро после записи.
- Антибот (настройка `roulette_guard`, по умолчанию включена) касается только бесплатных вращений, вращения за покупки не трогаются. Режим запрета: бесплатное вращение не начисляется, в `free_blocked` — «Бесплатные вращения для этого аккаунта недоступны», в журнал антибота раз в сутки — `roulette_denied`. Режим подтверждения: `spin` отвечает `{confirm: {token, text}}`, повтор с полем `confirm` проверяет кнопку «Я не робот» и крутит. Режим отметки: бесплатное вращение пишется в журнал (`roulette_noted` с номером вращения).

## Аналитика

Модуль `analytics` (`sn-modules/src/catalog/analytics/`), страница `/admin/m/analytics`, право «Деньги». Миграция `0240_analytics.sql`: таблицы `analytics_spans`, `analytics_islands`, `analytics_state` и индексы `payments (created_at)`, `orders (updated_at)`, `orders (paid_at) WHERE kind = 'trial'`.

- Выручка считается как на главной: оплаченные счета кроме «С баланса», минус возвраты, по дате оплаты, в валюте установки; звёзды отдельно. Месяц — по `remnawave.utc_offset_minutes`.
- Предрасчёт (`spans.rs`): каждый оплаченный заказ подписки (`new`, `renewal`, `change`; статус `paid`, `fulfilled` или `review`; сумма или звёзды больше нуля) даёт оплаченный период в `analytics_spans`. Продление начинается с конца прошлого периода той же подписки, новая и смена тарифа — с даты оплаты, смена обрезает прошлый период. Месячная стоимость — сумма заказа × 30 / дни. Периоды клиента с перерывом до 3 дней сливаются в отрезок `analytics_islands`.
- MRR на конец месяца — сумма месячных стоимостей действующих периодов. Платящие — клиенты с действующим отрезком; новые — начало первого отрезка; вернулись — начало следующего; ушли — конец отрезка, если за 3 дня не продлили; продлили — период, продолживший отрезок. Удержание — доля клиентов когорты (месяц первого отрезка) с действующим отрезком через 30, 60… дней после первой покупки; столбец появляется, когда срок наступил для всей когорты. LTV — чистые оплаты платящего клиента за всё время.
- Пересчёт: при открытии отчёта досчитываются клиенты, чьи заказы менялись с прошлого раза (с запасом 10 минут), под `pg_advisory_xact_lock`; если блокировка занята, а данные уже есть, отчёт не ждёт. Задача модуля `refresh` раз в 10 минут, раз в сутки пересчитывает всё заново. После полного или крупного пересчёта — `ANALYZE` этих таблиц.
- API: `GET /api/admin/m/analytics/report?months=N`, `?all=true` или `?from=ГГГГ-ММ&to=ГГГГ-ММ`, `source=` — отбор по UTM-метке (пустое значение — клиенты без метки). Части отчёта считаются параллельно на нескольких соединениях. Названия платёжек и способов — `CoreApi::payment_titles`, со своими названиями оператора. CSV собирает браузер: разделитель `;`, десятичная запятая, BOM.

## Поток покупки

1. Клиент выбирает тариф, срок и устройства. `checkout.quote` грузит тариф и текущую подписку, решает «продление или смена» по категории (`plan::classify`), собирает скидки модулей и считает цену (`pricing::quote`). Без явной подписки и при выключенных мультиподписках (`billing.multi_subscriptions`, по умолчанию выключены) текущей считается единственная живая подписка клиента: той же категории, иначе последняя (`plan::single_target`); при включённых — только пробная, иначе выдаётся новая. Поле `current` ответа описывает текущую подписку для предупреждения о переходе. Способы оплаты даёт реестр по валюте установки; «С баланса» всегда последний и недоступен, если денег не хватает на всю сумму.
2. `checkout.start` создаёт заказ со снимком тарифа (`TariffSnapshot`) и платёж `pending`, в той же транзакции вызывает `on_order_created` модулей и только потом просит провайдера выставить счёт. Мгновенный вебхук всегда найдёт свой платёж. Клиенту отдаётся `/api/pay/{payment}` — переход на страницу оплаты, который работает и во встроенном браузере Telegram на iOS.
3. Вебхук приходит на `/api/webhooks/pay/{провайдер}`. Провайдер проверяет подпись по сырому телу, и только после этого `inbox.handle` пишет вебхук в `webhook_inbox` (тело и безопасные заголовки). Затем одной транзакцией: блокировка платежа, сверка провайдера, транзакции и суммы с валютой, `payment → paid`, `order → paid`, `on_order_paid` модулей, задача `fulfill_order`, событие `payment_paid`. Если модуль отказал (например, поздняя оплата истёкшего счёта сверх лимита промокода), деньги принимаются, а заказ уходит на ручную проверку без задачи выдачи. Пополнение баланса зачисляется в журнал в той же транзакции.
4. Воркер берёт задачу. `fulfillment.run` выдаёт заказ на подписку под advisory-блокировкой подписки (`LockSpace::Subscription`; под ней же ручные дни, лимиты, блокировка доступа и действия с подпиской при возврате) и перечитывает заказ. Заказ ждёт другие заказы этой подписки, которые ещё в работе: оплаченные с сохранённым планом, оплаченные раньше него (кроме тех, у кого плана ещё нет и по платежу ждём возврат) и заказы на ручной проверке, у которых план применён или выдаётся после решения админа. План (`plan::plan`) с абсолютными значениями и исходным сроком `base_expire_at` сохраняется в заказ до первого вызова Remnawave. Срок в плане округляется вверх до целой секунды, со сроком Remnawave сравнивается с точностью до миллисекунды. После успешного запроса ставится `orders.plan_applied_at`, и повтор запрос не отправляет. Если перед повтором срок в Remnawave не равен ни исходному, ни целевому, заказ уходит на ручную проверку. Неприменённый план такого заказа помечается устаревшим (`orders.plan_stale_at`): он больше не применяется и не держит ни другие заказы подписки, ни автопродление. То же происходит, когда у задачи выдачи заказа на проверке кончились попытки. Дальше решает админ: «Пересчитать и выдать» или «Отметить выданным». Пока по платежу заказа ждём возврат (кроме возвратов повторных оплат), выдача откладывается; после отказа кассы или отмены заявки задача выдачи ставится снова. Заказ заблокированного клиента пользователя в Remnawave не создаёт. Если деньги пришли уже после блокировки (`paid_at` платежа не раньше `clients.blocked_at`), платёжка умеет возвраты, у заказа нет плана, а по оплате не было возвратов и заявок, выдача сама возвращает всю сумму (`PaymentInbox::refund_blocked`: та же механика, что у возврата из админки, от имени системы, под блокировкой строки клиента, ключ идемпотентности выводится из номера платежа). Подписка не меняется, аудит `payment.refund_blocked` или `payment.refund_blocked_requested`, клиенту уходит `payment.refunded_blocked` (для ожидающего возврата — после подтверждения кассы), задача выдачи завершается исходом `refunded`. В остальных случаях (баланс, касса без возвратов, оплата до блокировки, клиента разблокировали, касса отказала в возврате) заказ уходит на проверку, причина объясняет, почему оплату не вернули. Если клиента заблокировали во время выдачи, статус перепроверяется перед записью результата: пользователь Remnawave отключается, зеркало получает статус «отключена» (аудит `subscription.blocked_delivery`), уведомление о выдаче не уходит.
5. Выдача: `POST /api/users` или `PATCH /api/users`, при необходимости `reset-traffic`, затем свежий `GET` в зеркало и `order → fulfilled`. Повторное отключение и включение (ответы A029 и A030) считаются успехом. Имя нового пользователя — ник Telegram, без него часть почты до `@`, без неё `tg<Telegram ID>` или `id<номер клиента>` (`subscription::remna_name_base`, только латиница, цифры, `_` и `-`, до 36 символов); у второй подписки клиента `_2`, у третьей `_3`. Имя резервируется в `subscriptions.remna_username` при создании подписки. Если пользователь Remnawave с таким именем чужой (описание не `stealthnet client <uuid клиента>`) или имя занято другой подпиской, берётся следующий свободный номер; если имя заняли между расчётом плана и созданием, резерв меняется, план сбрасывается и выдача повторяется. Уже выданные подписки не переименовываются: Remnawave не умеет менять имя пользователя. При выключенных мультиподписках заказ на новую подписку — покупка клиента или выдача админом, — дошедший до выдачи, когда у клиента уже есть живая подписка (две оплаты или две выдачи до выдачи первой), привязывается к ней: покупка становится продлением или сменой, выдача админом остаётся выдачей и считается по категории (аудит `order.attached`).

Правила срока: продление (та же категория) — от `max(expireAt, дата оплаты)`, смена тарифа (другая категория или первая оплата после пробного) — от даты оплаты, оставшиеся дни не переносятся, трафик сбрасывается. Смена — это переход: подписка и пользователь Remnawave остаются те же (ссылка не меняется), сквады, лимиты и срок заменяются на новые. Бот, кабинет и мини-приложение перед оплатой пишут, что текущая подписка будет удалена, а новая станет доступна сразу.

Продление: при переходе с безлимита на лимит или при смене стратегии сброса счётчик трафика сбрасывается и ставится лимит тарифа; «Без сброса» прибавляет лимит, только если стратегия и до, и после — NO_RESET. Сквады, добавленные не тарифом, сохраняются: это текущие сквады минус сквады из снимка последнего выданного заказа. Если старый оплаченный срок ещё идёт, текущий лимит устройств держится до его конца (`subscription_device_holds`), потом обслуживание воркера снижает лимит до оплаченного в новом заказе и удаляет лишние устройства, начиная со старых. Смена тарифа и ручная правка доп. устройств снимают удержание.

Докупка к действующей подписке — модуль «Опции» (`sn_modules::catalog::options`), товары `devices` и `traffic`, оплата как у любого товара модуля: `POST /api/client/items/quote` и `POST /api/client/items/checkout` (`ItemRequest`), в боте — раздел «Докупить». Доп. устройства стоят месячную цену × число устройств × оставшиеся дни / 30 (`pricing::prorated`, дни округляются вверх, сумма — до шага валюты, звёзды — вверх, не меньше одной). Пакеты трафика (`tariffs.traffic_addon`: размер в ГБ, цены, звёзды и судьба остатка `burn`/`carry`) продаются только у тарифов с лимитом и стоят полную цену. Выдача идёт через ядро (`CoreApi::apply_device_addon`, `apply_traffic_addon`) после заказов подписки, которые ещё в работе: лимит устройств ставится абсолютным значением (`extra_devices` растёт, удержание устройств учитывается), лимит трафика — целью, сохранённой в `extra_traffic_orders` до запроса в Remnawave, поэтому повтор не прибавляет пакет дважды; подписка, у которой кончился трафик, включается. Докупленный остаток периода лежит в `subscription_extra_traffic` и расходуется после основного трафика: неизрасходованное — это `min(лимит − израсходовано, докуплено)`. При продлении в режимах «при оплате» и «без сброса» остаток сгорает или переносится по настройке тарифа (`plan::plan`), смена тарифа и ручной лимит админа его обнуляют. В режимах со сбросом по расписанию продление докупленное не трогает: после сброса в Remnawave обслуживание воркера (`settle_extra_traffic`) считает расход окна по `lifetimeUsedTrafficBytes` и ставит лимит «база + перенос»; если Remnawave не сбросила трафик за 6 часов после срока, сверка откладывается до следующего окна.

Промокоды: живой резерв (заказ `pending`, срок резерва или счёта не истёк) занимает лимиты `max_uses` и `per_client`, поэтому второй счёт по одноразовому коду до оплаты, отмены или истечения первого получает отказ. Резерв берётся под блокировкой клиента и строки промокода, использование пишется при оплате в той же транзакции; при поздней оплате лимиты проверяются заново. Несуществующий и неподходящий код дают одинаковый ответ `promo.not_found`. Попытка засчитывается до проверки кода и прощается, если код подошёл; после 10 неудач клиента или 30 неудач с одного адреса за 15 минут — 429 `promo.rate_limited` (IPv6 считается по сети /64, внутренние адреса прокси не считаются, бот ограничен только по клиенту). Расчёт и оформление корзины с промокодом считают неудачи так же, но отвечают 422 `module.invalid`. Код неверного формата отклоняется без обращения к базе. Проверка и активация доводятся до конца, даже если клиент оборвал запрос.

Оплата с баланса — та же схема без провайдера: списание в журнал, платёж `paid` и задача выдачи в одной транзакции. Смешанной оплаты нет.

Повторная оплата уже оплаченного счёта с другой транзакцией провайдера — отдельный платёж `method = repeat`: сумма в валюте установки зачисляется на баланс, звёзды и другая валюта уходят на ручную проверку (`payment_repeats`, аудит `payment.repeat_credited` или `payment.repeat_review`, уведомление клиенту).

Возврат через платёжную систему без подтверждения (`completed = false`) записывается в `provider_refunds` как ожидающий: статус платежа и подписка не меняются, пока касса не подтвердит его вебхуком или опросом `fetch_refund` (задача `poll_payment` и обслуживание воркера). Отказ кассы (`RefundDeclined`) снимает ожидание. Сумма ожидающего возврата пополнения сразу удерживается записью `refund_hold`; отказ кассы или отмена возвращают её записью `refund_release`, подтверждение второго списания не делает. Действие с подпиской выполняется после подтверждения и при сбое повторяется из обслуживания воркера (пауза от минуты до часа, 12 попыток), затем аудит `subscription.refund_action_failed` и ручное решение. Если после запроса возврата по подписке прошла новая оплата (любой заказ подписки, кроме пополнения, пробного и выдачи админом, оплаченный позже записи аудита `payment.refund_requested`), отключение или укорочение не применяется и сразу ждёт решения админа (`refund.action_conflict`, `PaymentsRepo::paid_after_refund`). Опрашиваются только заявки систем с `supports_refund_polling`, по очереди времени последнего опроса. Ручной разбор — с правом «Возвраты»: `GET /api/admin/refunds/pending` — ожидающие заявки, `POST /api/admin/refunds/{id}/cancel` — отменить с пояснением (удержание возвращается), `POST /api/admin/refunds/{id}/confirm` — подтвердить вручную с пояснением, `GET /api/admin/refunds/actions` — несработавшие действия с подпиской, `POST /api/admin/refunds/{id}/action/retry` и `POST /api/admin/refunds/{id}/action/close` — повторить действие или закрыть с пояснением. Все действия пишутся в аудит.

Звёзды: счёт — `createInvoiceLink` с ценой в звёздах из тарифа. Бот получает `pre_checkout_query` и `successful_payment` и передаёт их в `inbox.stars_pre_checkout` и `inbox.stars_payment`; HTTP-вебхуков у звёзд нет. Оплаты и возвраты из пачки `getUpdates` сначала записываются в `bot_star_events`, и только потом бот сдвигает смещение. Непроведённые события бот повторяет сам (пауза от 30 с до 30 мин) и раз в минуту сверяет `getStarTransactions` от курсора `telegram.stars_offset.<id бота>`; расхождения уходят на ручную проверку (`payment.stars_review`). События на ручной проверке разбирает администратор с правом «Деньги»: `GET /api/admin/stars/review` — список, `POST /api/admin/stars/review/{id}/refund` — вернуть звёзды через `refundStarPayment` по списанию и плательщику (повтор безопасен), `POST /api/admin/stars/review/{id}/close` — закрыть с обязательным пояснением. Действия пишутся в аудит (`payment.stars_review_refunded`, `payment.stars_review_refund_failed`, `payment.stars_review_closed`). Уведомление Telegram о возврате списания, которое не проводилось как оплата, платежи не меняет.

## Очередь и периодические работы

- `jobs.dedupe_key` уникален только среди задач `queued` и `running`: выполненную или ушедшую на проверку задачу можно поставить снова (`ensure_queued`).
- Воркер берёт задачи по одной с токеном аренды и продлевает аренду каждую треть её срока. Итог записывает только владелец аренды.
- Обслуживание, раз в минуту: отмена просроченных счетов, чистка `webhook_inbox`, опрос ожидающих возвратов и повтор действий с подпиской после возврата, снятие удержанных доп. устройств, сверка докупленного трафика после сброса.
- Досверка выдачи, раз в 5 минут: заказ `paid`, оплаченный больше 2 минут назад, без активной задачи, у которого последняя задача затихла больше 30 минут, ставится в очередь снова (аудит `order.redeliver`). Заказ с ожидающим возвратом досверка не берёт. Заказ на ручной проверке решает админ (право «Деньги»): список `GET /api/admin/orders/review`, «Повторить выдачу» `POST /api/admin/orders/{id}/redeliver`, «Пересчитать и выдать» `POST /api/admin/orders/{id}/recalculate`, «Отметить выданным» `POST /api/admin/orders/{id}/mark-fulfilled`. Каждое действие пишется в аудит заказа.
- Автопродление выбирает подписки в SQL постранично: незавершённые, с включённым автопродлением, в окне списания и повторов. Списание с карты держит платёж до конца окна повторов плюс день, а задачу `poll_payment` ставит в одной транзакции с платежом до запроса к кассе. Неизвестный исход уточняется статусом по номеру платежа или повтором запроса с тем же ключом идемпотентности в течение 20 часов. Повтор уходит, только пока продление ещё нужно: клиент не заблокирован, автопродление включено, подписка не завершена и не отключена, её срок равен циклу попытки, нет другого оплаченного и не выданного заказа подписки. Иначе новый запрос не отправляется, платёж ждёт ручной проверки (аудит `payment.autorenew_unclear`). Блокировка клиента не отменяет автосписание с невыясненным исходом: подтверждённую оплату выдача возвращает автоматически или отдаёт на ручную проверку по правилу для заблокированных (аудит `payment.autorenew_blocked`), отказ кассы отменяет платёж и заказ, разблокировка возобновляет опрос. Если автопродление выключили, пока списание было в пути, подписка всё равно продлевается, а клиент вместе с обычным уведомлением получает `autorenew.charged_after_off`: новая дата окончания и предложение написать в поддержку, если продление не нужно. Заказ на ручной проверке держит автопродление, только если его план применён или выдаётся либо заказ оплачен самим автопродлением.
- Раз в час подписка, истёкшая больше `max(90, retry_days + 8)` дней назад и без открытых заказов, получает `ended_at`, если это не откроет клиенту пробный период. Покупка такой подписки снимает `ended_at`.

## Связь с Remnawave

- Клиент: таймаут 12 с, без редиректов, `Bearer`-токен, необязательная кука защиты, для `http://` внутри docker-сети — заголовки `X-Forwarded-For` и `X-Forwarded-Proto: https`, без них панель рвёт соединение.
- Ошибки: `NotFound` — пользователя нет; `Timeout`, 5xx и обрыв — исход неизвестен (`outcome_unknown`), перед повтором нужна сверка; 400 с кодом `A0xx` — отказ панели.
- Подключение (адрес, токен, кука, секрет вебхуков) хранится в настройках и зашифрованных секретах; переменные окружения — запасной вариант для первого запуска. `Services::reload` пересоздаёт клиента без перезапуска.
- Вебхуки: `POST /api/remnawave/webhook`, подпись `X-Remnawave-Signature` = HMAC-SHA256 сырого тела секретом `WEBHOOK_SECRET_HEADER`. Повтор отсекается по SHA-256 тела. В базу пишется тело без `vlessUuid`, паролей и ссылки подписки. Обработка — задачей `process_remna_event`: зеркало обновляется, только если `updatedAt` из события не старше сохранённого.
- Вебхук — быстрый сигнал, а не истина: события теряются, если сервис лежал дольше 15 секунд. Сверка `remna_sync.reconcile` по `stale_mirrors` обязательна.
- Массовые операции — только `bulk/*` по спискам до 500 id, `bulk/all/*` не используем.

## Валюта и звёзды

- Валюта установки — настройка `core.currency`. Цены периодов и доп. устройств хранятся по валютам (`price_usd_minor`, `price_rub_minor`), видна только цена валюты установки; периоды без неё не продаются.
- Скидки: в долларах — до цента, в рублях — до целого рубля (на экранах рубли без копеек). Проценты округляются половиной вверх.
- Звёзды — отдельная цена у срока и у доп. устройства. Процентная скидка в звёздах округляется до целой звезды, фиксированная к звёздам не применяется. Пополнять баланс звёздами нельзя.
- Баланс ведётся журналом `balance_entries`; остаток в `client_balances` с `CHECK (amount_minor >= 0)` меняется в той же транзакции. Реферальные начисления — отдельный кошелёк, вывод только из него.

## Безопасность входящих запросов

- Платёжные вебхуки: подпись проверяет провайдер по сырым байтам и в постоянное время. Платёж сверяется по провайдеру, транзакции, сумме и валюте; недоплата не засчитывается никогда. Ответ 2xx — только когда событие записано и обработано или сознательно пропущено; при внутренней ошибке — 503, чтобы провайдер повторил. Повтор тела с неверной подписью не мешает настоящему уведомлению. Повтор уже обработанного вебхука получает ответ в формате провайдера.
- Неизвестная платёжная система получает 404, тело больше 64 КиБ — 413, оба ответа до записи в базу. Уведомления принимает любая настроенная система, даже выключенная: `enabled` влияет только на показ способа и новые счета. Ненастроенная система получает 404, отказ пишется без тела (`not_accepted`). Тело сохраняется только после проверки подписи. Отказы пишутся без тела, не больше 30 записей с одного адреса за 10 минут (IPv6 — по /64). Принятые записи и подлинные уведомления, отклонённые проверкой (`rejected_business`), хранятся 30 дней; отказы по подписи и записи без тела — 3 дня. Для систем, которые проверяют подлинность запросом к своему API (ЮKassa, Overpay), с одного адреса проходит не больше 10 непроверенных уведомлений в минуту, дальше 429; у ЮKassa ненайденный идентификатор помнится 60 секунд.
- `accepts_http_webhooks = false` у баланса и звёзд: их нельзя «оплатить» HTTP-запросом.
- Overpay не подписывает уведомления. Адрес уведомлений уходит в каждом счёте (`options.webhookUrl`) с токеном в пути: HMAC-SHA256 от закрытого ключа клиентского сертификата и номера проекта. Уведомление без токена или с чужим токеном отклоняется без запроса к Overpay. Уведомление принимается методами POST и GET: у GET берётся строка запроса, а без неё — тело, как в спецификации Overpay. Из тела берётся только номер заказа, статус, сумма списания (`amount_charged`) и наш платёж (`merchant_order_id`) читаются запросом `GET /api/orders/{id}`. Все запросы к Overpay идут с клиентским сертификатом (mTLS) из настройки в формате PEM; клиент `reqwest` с сертификатом собирается один раз на текст сертификата.
- Мини-приложение: `initData` проверяется по HMAC от токена бота, повтор ключей отклоняется, срок жизни — час. Токен приходит в теле ответа и передаётся только в `Authorization: Bearer`: куку мини-приложению не ставим, его сессии по куке не принимаются.
- Изменяющие запросы (POST, PUT, PATCH, DELETE), авторизованные кукой клиента или админа, принимаются только со своего сайта: `Origin` из `SN_PUBLIC_URL`, адреса в настройках или `SN_CORS_ORIGINS`, либо `Sec-Fetch-Site: same-origin` или `none`, а без `Sec-Fetch-Site` — `Origin`, совпадающий с `Host`. Иначе 403 `auth.cross_site`. Запросы с `Bearer` и запросы без `Origin` и `Sec-Fetch-Site` эта проверка не касается.
- Вход админа: лимиты считают только неудачи пароля — 10 за 15 минут на пару почта и адрес и 20 за 15 минут на почту; с одного адреса — 30 любых попыток за 5 минут. Общий лимит на почту не действует на адрес, с которого этот админ успешно входил за последние 30 дней (`admin_login_addresses`): перебор с чужих адресов не закрывает вход с привычного. Во всех лимитах по адресу IPv6 считается по сети /64. Неверный код TOTP после верного пароля: 5 за 15 минут и 20 за сутки на админа, дальше 429 и аудит `admin.totp_locked`.
- Сессии админов и клиентов — случайные токены, в базе только SHA-256. Пароли — argon2id, старые bcrypt-хеши принимаются при входе.
- Администраторы (право `admins`, по умолчанию только у владельца): `GET/POST /api/admin/admins`, `POST /api/admin/admins/{id}/role|disable|enable|password|2fa/reset`. Новому администратору и при сбросе пароль придумывает сервер (16 знаков без похожих символов) и отдаёт один раз; у такого админа `must_change_password`, и админка не пускает дальше экрана смены пароля. Себя менять нельзя (`admins.self`), владельцами распоряжается только владелец (`admins.owner_only`), последнего действующего владельца нельзя понизить или отключить (`admins.last_owner`, проверка под `FOR UPDATE` по владельцам). Отключение и сбросы закрывают все сессии этого админа; сессии отключённого не принимаются уже на поиске токена. Каждое действие пишется в аудит (`admin.created`, `admin.role_changed`, `admin.disabled`, `admin.enabled`, `admin.password_reset`, `admin.totp_reset`). Свой пароль и вход по коду админ меняет на странице «Безопасность» (`/auth/password`, `/auth/2fa/*`).
- API-ключи (право `settings`): `GET/POST /api/admin/api-keys`, `POST /api/admin/api-keys/{id}/revoke`. Токен `snk_…` из 24 случайных байт показывается один раз, в базе только SHA-256 и первые 12 знаков для списка. Ключ передаётся как `Authorization: Bearer`, кукой не принимается. Права ключа выбираются при создании и не шире прав создателя; при каждом запросе они ещё раз пересекаются с текущими правами создателя, а у отключённого создателя ключ не работает. Ключ не получает права `admins`, не управляет ключами и не трогает `/auth/password`, `/auth/security`, `/auth/2fa/*`. Срок — по часам сервиса, «последнее использование» обновляется не чаще раза в минуту. Создание и отзыв пишутся в аудит (`api_key.created`, `api_key.revoked`).
- Регистрация по почте, три варианта (модуль `mail`, поле `transport`): `none` — по умолчанию, без подтверждения: `POST /api/client/auth/email/register` и `/email/password` (почта и пароль от 10 знаков, argon2id в `client_passwords`, почта помечается неподтверждённой, сессия через `cabinet_session` с проверкой 2FA); `smtp` и `resend` — вход кодом из письма на 15 минут (`/auth/email`, `/auth/email/verify`), письмо уходит через `lettre` по SMTP (STARTTLS/TLS/без, таймаут 20 с) или `POST https://api.resend.com/emails` с ключом. В режиме пароля код отвечает `auth.email_password_mode`, в режиме кода пароль — `auth.email_code_mode`. `/api/public/site` отдаёт `email_auth`: `password`, `code` или `null`, если вход на сайт выключен. Проверочное письмо — `POST /api/admin/mail/test` (право `settings`, только из сессии). Раздел «Настройки → Почта и уведомления».
- Доступ клиентов (`core.client_access`, «Настройки → Кабинет и мини-приложение»): `miniapp` — мини-приложение в Telegram (кнопка `web_app` «Открыть приложение» в главном меню бота и кнопка меню чата через `setChatMenuButton` на `{адрес сайта}/app`, только при https; бот ставит и снимает кнопку меню сам и помнит своё состояние в `bot.menu_button`, ручную настройку в BotFather не трогает), `site_login` — вход в кабинет на сайте, `self_devices` и `self_reissue` — отключать свои устройства и выпускать новую ссылку. Выключенное закрывается на сервере: вход в мини-приложение — `auth.miniapp_off`, вход на сайт — `auth.site_off`, уже открытые сессии этого канала перестают приниматься, действия клиента — `client.action_off` (админ может всё). Флаги отдаются в `/api/public/site` → `client_access`, бот, кабинет и мини-приложение прячут кнопки.
- Секреты в базе зашифрованы AES-256-GCM ключом `SN_SECRET_KEY`, имя настройки участвует в шифровании, поэтому секрет нельзя подменить другим.
- Реальный IP клиента берётся из `X-Forwarded-For` только от доверенных прокси: цепочка разбирается справа до первого недоверенного адреса. Пустой `SN_TRUSTED_PROXIES` означает loopback и шлюз Docker (внутри контейнера), явный список адресов и сетей CIDR заменяет умолчания. Если первые 20 запросов пришли от доверенного прокси без `X-Forwarded-For`, в журнал один раз пишется предупреждение, что прокси не передаёт адрес клиента.

## Хранилище

- Ключи `bigint identity`, наружу — `public_id uuid`. Время — `timestamptz`, соединения работают в UTC. Перечисления — `text` с `CHECK`, без типов `enum` в PostgreSQL. Снимки цены, тарифа и плана — `jsonb` в заказе.
- Миграции — `crates/sn-store/migrations`, применяются `sqlx` (`stealthnet migrate` или при `serve`) с контрольными суммами. Выпущенную миграцию не правим, только добавляем новую.
- Идемпотентность: `UNIQUE` на `(provider, provider_txid)`, `balance_entries.idempotency_key`, `jobs.dedupe_key` (среди активных задач), `remna_events.body_sha256`, `webhook_inbox (source, dedupe_key)`, `bot_star_events (charge_id, event)`, `event_deliveries (event_id, module)`.

## Перенос из другого бота

Операторы переезжают со STEALTHNET 7.x (Node, Prisma) и с бота Бедолаги (Python). Код — `sn_services::legacy`, экран — «Настройки → Перенос из другого бота» (права «Настройки» и «Деньги», только из сессии), команда — `stealthnet import-legacy [--dry-run] [файл]`; без файла она читает базу 7.x по `LEGACY_DATABASE_URL` через `row_to_json`. Код и данные старых систем не меняются, клиентам ничего не отправляется: перенос не ставит задач и не пишет событий.

1. Файл. `POST /api/admin/import/upload?source=…&name=…` принимает сырое тело потоком на диск (`SN_IMPORT_DIR`, по умолчанию временная папка), до 2 ГБ, общий лимит тела к маршруту не применяется. Формат определяется по содержимому: `pg_dump` в виде SQL (бэкап 7.x `.sql` и `.sql.gz`, `database.sql` Бедолаги), JSON ORM-выгрузки Бедолаги (`database.json` в `.tar.gz` вместе с `metadata.json`), zip с паролем AES (так бот Бедолаги шлёт копию при `BACKUP_ARCHIVE_PASSWORD`). Пароль спрашивается один раз: архив распаковывается рядом, исходный zip удаляется. Таблицы читаются потоком, ненужные (журналы вебхуков, мониторинг) пропускаются, не попадая в память. Источник определяется по таблицам: если оператор ошибся с выбором, проверка переключит его сама.
2. Проверка (`import_runs.state = checking → ready`) ничего не пишет, кроме самого прогона и списка проблем (`import_issues`). Она сводит обе выгрузки к одной модели (`legacy::model`), читает всех пользователей Remnawave постранично (`/api/users/stream`, по 500) и сопоставляет подписки: номер пользователя 3.x, `shortUuid` (в том числе из ссылки подписки), Telegram ID, почта, имя; один пользователь Remnawave достаётся одной подписке, при нескольких кандидатах выбирается совпадение срока до 36 часов или имени с суффиксом `_N`, иначе подписка уходит в отчёт. UUID от Remnawave 2.x напрямую не разрешается: в 3.x его нет, поэтому такие подписки находятся по ссылке, Telegram ID или почте. Ответ — счётчики, сумма балансов, план по валюте, сколько клиентов совпало с уже существующими, и список «что не перенесётся» простыми словами.
3. Перенос (`running → done`) идёт фоновой задачей сервера пачками по 400 записей (платежи по 1000), каждая пачка в своей транзакции, ход пишется в `import_runs.progress`. Только один перенос одновременно (`import_runs_running_key`). После перезапуска сервера незавершённый перенос становится `interrupted`, его можно запустить снова.
4. Повтор безопасен. Связь со старыми id хранится в `legacy_ids` с префиксом источника (`stealthnet:client`, `bedolaga:payment` …), у клиента там же — уже зачисленный баланс. Повторный перенос свежей выгрузки добавляет только новое и доводит баланс до значения в старой системе: прибавка — запись `migration_opening`, убыль — `admin_adjust` от имени запустившего, но не больше остатка. Клиенты, которые уже есть в установке, находятся по Telegram ID, затем по почте и не задваиваются.

Что куда переносится:

- Валюта. У Бедолаги — рубли. У 7.x — валюта всех оплат, при двух валютах — `default_currency`; баланс клиентов, плативших в обеих валютах, не переносится и уходит в отчёт. Если в установке ещё не было оплат и балансов, валюта установки переключается на валюту источника, иначе деньги пишутся в валюте источника с предупреждением.
- Клиенты: Telegram (с ником и именем), почта (подтверждённая у 7.x, по флагу у Бедолаги), Google и Apple, пароль bcrypt — в `client_passwords`, блокировка 7.x, язык, недоступность бота, UTM. «Заблокирован» у Бедолаги означает и остановившего бота, поэтому такие клиенты переносятся без блокировки, с отметкой недоступности бота и строкой в отчёте. Тем, у кого был пробный период или подписка, ставится отметка «пробный уже брал».
- Тарифы и категории переносятся как есть, с периодами и ценами в валюте тарифа; тариф в другой валюте или со сквадом, которого нет в Remnawave, снимается с продажи. Сброс трафика: `on_purchase` → при оплате, `monthly` → месяц, `monthly_rolling` → скользящий месяц, `carry_over` → без сброса с пометкой. У Бедолаги без тарифов (режим «классика») подписки раскладываются по тарифам «серверы и трафик» с названием из свойств, например «Нидерланды, Германия · 50 ГБ», устройства — минимум группы, остальное — доп. устройства; такие тарифы создаются без цен и не продаются, пока оператор их не задаст.
- Подписки привязываются к найденному пользователю Remnawave (номер, имя, `shortUuid`), зеркало заполняется из того же ответа. Новых пользователей Remnawave перенос не создаёт и существующих не меняет. Сохраняются тариф, доп. устройства и автопродление с периодом.
- Платежи — история: заказ `fulfilled` (`refunded` для возвратов) с `PurchaseIntent::Imported` и платёж `paid` в валюте оплаты, звёзды — в XTR, исходные номера — в `provider_payload.imported`, без `provider_txid`. Неоплаченные счета и выдачи без денег не переносятся. Выдача такие заказы не берёт.
- Промокоды: скидка в процентах, суммой и дни; код приводится к верхнему регистру, недопустимые и другие виды (бонус на баланс, промогруппы) — в отчёт; использования — в `promo_redemptions`. Реферальные связи и коды (код без дефиса и пробелов) — в таблицы модуля «Рефералы».
- Обращения с перепиской; вложения остаются в старой системе, в тексте об этом пометка. Открытые обращения, где последним писал клиент, попадают в очередь поддержки.
- В отчёт и в «что не перенесётся»: подписки без пользователя Remnawave, неоднозначные и уже привязанные к другому клиенту, смешанные балансы, ждущие решения заявки на вывод, неактивированные подарки, товары, которых нет в новой системе (прокси, sing-box), удалённые пользователи Бедолаги. Отчёт — `GET /api/admin/import/{id}/report`, CSV через точку с запятой.

После переноса сверяется сумма балансов: зачисленное записями переноса равно сумме балансов выгрузки, расхождение — строка в отчёте. Проверено на синтетических выгрузках по 20 тыс. клиентов обоих форматов: около 30 секунд на отладочной сборке.

## Что работает и чего ещё нет

Работает и покрыто тестами:

- Покупка: расчёт цены со скидками модулей, счёт у платёжной системы или оплата с баланса, пополнение баланса, пробный период.
- Платёжные системы: Crypto Pay, Heleket, Lava.top, ЮKassa, Platega, ЮMoney, CloudPayments, Overpay, звёзды Telegram и баланс. Вебхуки, опрос счёта, повторные оплаты, возвраты на баланс и через кассу, ожидающие возвраты. У платёжки может быть несколько способов оплаты (`PaymentProvider::methods`): оператор включает нужные в настройке платёжки (`ProviderSettings.methods`), каждый становится отдельной кнопкой у клиента, выбранный код уходит в `InvoiceRequest.method` и сохраняется в `payments.pay_method`; без выбора остаётся одна кнопка, как раньше.
- Выдача в Remnawave: новая подписка, продление, смена тарифа, пробный период; повторы, досверка и ручной разбор заказов.
- Подписки: дни и лимиты вручную, сброс трафика, устройства, перевыпуск ссылки, блокировка и разблокировка клиента, автопродление с баланса и сохранённой карты, завершение давно истёкших.
- Связь с Remnawave: вебхуки, зеркало, сверка, ноды и сквады.
- Вход: админ с паролем и TOTP, мини-приложение, вход на сайт через бота.
- API админки: главная и лента, клиенты, платежи и возвраты, заказы, заявки на возврат и оплаты звёздами на ручной проверке, тарифы и категории, настройки, платёжные системы, модули, поддержка. Главная показывает счётчики ручной работы: `orders_review`, `stars_review`, `refund_actions_failed`.
- API кабинета и мини-приложения: каталог, расчёт, оформление, пополнение, история оплат, подписки, устройства, автопродление, поддержка. `GET /api/client/payments?limit=&before=` отдаёт только свои платежи, новые сверху, курсор — `public_id` последнего платежа страницы: что оплачено (вид заказа, тариф и срок или «Пополнение баланса»), сумма, возвращённая часть, способ словами, состояние, даты и ссылка `/api/pay/{id}` для неоплаченного счёта, пока он не истёк; номеров транзакций, ответов платёжной системы и внутренних id нет. `GET /api/client/topup` отдаёт баланс, пределы суммы, готовые суммы (общие с ботом, `pricing::topup_presets`) и способы оплаты для канала сессии; при выключенном балансе — 422 `balance.disabled`. `POST /api/client/topup` принимает `return_url` с адреса панели.
- Несколько подписок в кабинете и мини-приложении: при двух и больше живых подписках вверху переключатель (тариф, для подписок на одном тарифе — тариф и ник Remnawave, иначе «Подписка N»; срок и состояние). Выбор хранится в `?sub=ID` и `localStorage` (`sn.cabinet.sub`, `sn.mini.sub`), от него зависят подключение, устройства, автопродление, продление и докупка. `GET /api/client/me` отдаёт `multi_subscriptions`: при включённом режиме оплата предлагает «Продлить …» (запрос с `subscription_id`) или «Новая подписка» (без него; пробный период сервер берёт как текущую подписку). При выключенном режиме и нескольких старых подписках «Новой подписки» нет, как в боте.
- Поддержка: настройка `core.support_mode` — `tickets` (обращения в боте, кабинете и мини-приложении), `link` (кнопки ведут на `core.support_url`, новые обращения через API — 422 `support.tickets_off`) или `both`. Без сохранённого режима: есть ссылка — `both`, нет — `tickets`. `/api/public/site` отдаёт действующую ссылку `support_url` (в режиме обращений — `null`) и `support_tickets`. Бот по `/start support` сразу просит описать вопрос; мини-приложение при обращениях открывает эту ссылку бота.
- Бот: покупка, оплата звёздами, вход на сайт, уведомления.
- Уведомления администраторам: бот раз в минуту проверяет новые сообщения клиентов в поддержку, заказы на ручной проверке, оплаты звёздами на разборе, незавершённые возвраты, автоматические возвраты заблокированным клиентам (курсор по аудиту) и заявки на вывод (`sn-services/src/alerts.rs`, состояние в `bot_state`, при первом запуске только запоминает текущее) и пишет в одну группу Telegram (`sn-bot/src/alerts.rs`). Группа подключается ссылкой `startgroup=alerts_<код>`, настройки — ключ `alerts.telegram`, темы бот создаёт сам (`createForumTopic`) и пересоздаёт, если их удалили; при переходе группы в супергруппу адрес обновляется сам.
- Почта: отправка через SMTP или Resend отдельно от способа входа (пароль или код из письма). Уведомления тем, кому нельзя написать в Telegram, уходят письмом (`NotifyHandler` в `sn-bot`): окончание подписки и автопродление, оплаты, ответы поддержки, каждое выключается. Пароль клиента: восстановление кодом из письма (`/api/client/auth/email/reset`, `/reset/confirm`), смена в кабинете (`/api/client/security/password`), временный пароль из админки (`/api/admin/clients/{id}/password`).
- Модули: промокоды, рефералы, UTM-метки, доп. опции, рассылки в бот и на почту — разовые и автоматические по событиям, подарочные подписки, промо-ссылки, антибот, лимиты трафика, конкурсы, рулетка, бизнес-аналитика. Остальные из каталога — заглушки: ИИ-чат, вход через Google и Apple. «Собери сам», Gramads, прокси SOCKS5/HTTP, sing-box, AmneziaWG, «Мой налог» и маркетплейс убраны из каталога: их не будет.

Ещё не написано:

- Ручная правка доп. устройств у подписки без оплаченного периода отвечает `not_implemented`.
