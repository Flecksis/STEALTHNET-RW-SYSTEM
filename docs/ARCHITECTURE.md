# Архитектура STEALTHNET на Rust

## Опорные решения

- Remnawave 3.4.11 — источник истины по VPN: пользователь, срок, статус, трафик, устройства, ноды, сквады, хосты. Хосты (названия серверов в приложении, адреса, порядок) у себя не храним: вкладка «Хосты» и блок сквада «Что видят клиенты» читают и меняют их прямо в Remnawave. У себя храним ссылку на пользователя (числовой `id`, `shortUuid`) и зеркало для списков и лент. Решения о доступе принимаем по свежему ответу Remnawave.
- Деньги живут только в нашей базе: заказы, платежи, журнал баланса. Суммы — целые минорные единицы, без `float` и `numeric`.
- Валюта у установки одна: доллары по умолчанию или рубли. У звёзд Telegram своя цена в тарифе, курса нет.
- Тарифы и категории создаёт оператор. Код опирается только на свойства тарифа: категория, сроки, цены, устройства, лимит и сброс трафика, сквады.
- Оплата и выдача разделены. Вебхук в одной транзакции отмечает платёж и ставит задачу выдачи; воркер применяет заказ к Remnawave, повторяя при сбоях.

## Крейты и границы

```
sn-domain ← sn-remnawave
          ← sn-store
          ← sn-payments
          ← sn-modules (+ sn-store, axum)
          ← sn-services (+ все выше)
                ← sn-server, sn-worker, sn-bot
                        ← sn-app
```

| Крейт | Отвечает за | Не делает |
|---|---|---|
| `sn-domain` | Типы и правила: `Money`, `Stars`, `Tariff`, `quote`, `plan`, статусы заказа и платежа, `DomainEvent`, `ModuleId` и каталог | Ввод-вывод, время берёт аргументом |
| `sn-remnawave` | `RemnawaveApi` (типаж), `RemnawaveClient` (HTTP), модели, `webhook` (подпись, разбор, удаление секретов), `fake::FakeRemnawave` для тестов | Знает о наших заказах |
| `sn-store` | `Store`, `Db` (общий для соединения и транзакции), репозитории, миграции, `SecretBox` | Бизнес-решения: принимает готовые данные и проверяет переходы статусов |
| `sn-payments` | `PaymentProvider`, `ProviderRegistry`, провайдеры | Ходит в базу |
| `sn-modules` | `Module`, `ModuleRegistry`, `CoreApi` (что ядро даёт модулям), закрытие маршрутов выключенного модуля | Ходит в Remnawave |
| `sn-services` | `Services` и сценарии: `auth`, `clients`, `checkout`, `inbox`, `fulfillment`, `subscriptions`, `remna_sync`, `autorenew`, `events`, `stars_review` | HTTP |
| `sn-server` | Маршруты, извлечение сессий, перевод ошибок в HTTP | Бизнес-логика: только вызов сценариев |
| `sn-worker` | Очередь `jobs` (`FOR UPDATE SKIP LOCKED`, аренда с токеном, повторы), рассылка событий модулям, периодические работы: обслуживание, автопродление, сверка, досверка выдачи, завершение давно истёкших подписок | — |
| `sn-bot` | Long polling, экраны, оплата звёздами через `inbox().stars_*` с журналом `bot_star_events` и сверкой `getStarTransactions` | Свои правила цены и выдачи |
| `sn-app` | Конфиг из окружения, логи, команды `serve`, `migrate`, `create-admin`, `gen-secret-key`, `import-legacy` (перенос ещё не написан) | — |

Публичные типы `sn-domain` и типажи `RemnawaveApi`, `PaymentProvider`, `Module`, `CoreApi` — контракт для всех крейтов. Менять их можно только добавлением, без переименований.

## Ядро и модули

Ядро работает всегда: клиенты и подписки, тарифы и пробный период, платежи и автопродление, поддержка, ноды, сквады и хосты, бот, кабинет и мини-приложение, настройки и доступы.

Модуль — реализация `sn_modules::Module` с одним из 23 `ModuleId` из каталога (`sn_domain::module::CATALOG`, данные из макета «Модули»). Пока модуль не написан, на его месте `Placeholder`: в админке он виден и переключается, но ничего не делает.

Что модуль может:

- отдать маршруты админки и клиента: они монтируются на `/api/admin/m/{id}/…` и `/api/client/m/{id}/…`, вход проверяет сервер, а выключенный модуль отвечает 404 `module.disabled` без перезапуска. Сервер кладёт в расширения запроса клиента его адрес (`sn_modules::catalog::web::ClientAddr`), посчитанный по тем же правилам доверенных прокси, что и для лимитов входа;
- поправить цену: `quote_adjustments` возвращает скидки, их применяет `sn_domain::pricing::quote`. Хуки цены (`quote_adjustments`, `quote_item`) ядро вызывает, уже отпустив своё соединение с базой: модуль берёт соединение сам, и расчёты не исчерпывают пул;
- участвовать в заказе: `on_order_created`, `on_order_paid`, `on_order_canceled` вызываются в транзакции ядра. Отказ (`ModuleError::Invalid`) при создании отменяет оформление, при оплате отправляет заказ на ручную проверку без выдачи;
- реагировать на события ядра: `on_event` получает `DomainEvent` из таблицы `domain_events` (outbox), воркер раздаёт их каждые 2 секунды. Получатели — модули, включённые при первой раздаче. После ошибки модуля событие повторяется: пауза 5 с, удваивается до часа, всего 12 попыток (около 3,4 ч), затем доставка уходит на ручную проверку (`event_deliveries`, аудит `module.event_review`). Пока у модуля висит более раннее событие клиента, следующие события этого клиента ему не отдаются. Выключенный модуль событие не держит. Разбор в админке: `GET /api/admin/events/review`, `POST /api/admin/events/{id}/retry`;
- работать по расписанию: `tasks` и `run_task`;
- добавить кнопки в бот: `bot_entries`;
- менять баланс, дни подписки и ставить задачи только через `CoreApi`.

Чего модуль не делает: не вызывает Remnawave сам и не пишет в `client_balances` напрямую. Свои таблицы модуль создаёт своей миграцией в общей последовательности, поэтому таблицы выключенного модуля существуют и данные не теряются.

Как подключить модуль:

1. Реализовать `Module` в `sn-modules/src/catalog/<id>.rs` (или в отдельном крейте `sn-mod-<id>`).
2. Передать экземпляр в `ModuleRegistry::new(vec![…])` в `sn-app`.
3. Если нужны таблицы — миграция `crates/sn-store/migrations/<номер>_<id>.sql`.
4. Настройки описать через `settings_schema`: форма в админке строится по схеме, секреты хранятся зашифрованными.

«Мой налог» доступен только при валюте «Рубли»: реестр не даёт его включить и считает выключенным при долларах.

## Поток покупки

1. Клиент выбирает тариф, срок и устройства. `checkout.quote` грузит тариф и текущую подписку, решает «продление или смена» по категории (`plan::classify`), собирает скидки модулей и считает цену (`pricing::quote`). Без явной подписки и при выключенных мультиподписках (`billing.multi_subscriptions`, по умолчанию выключены) текущей считается единственная живая подписка клиента: той же категории, иначе последняя (`plan::single_target`); при включённых — только пробная, иначе выдаётся новая. Поле `current` ответа описывает текущую подписку для предупреждения о переходе. Способы оплаты даёт реестр по валюте установки; «С баланса» всегда последний и недоступен, если денег не хватает на всю сумму.
2. `checkout.start` создаёт заказ со снимком тарифа (`TariffSnapshot`) и платёж `pending`, в той же транзакции вызывает `on_order_created` модулей и только потом просит провайдера выставить счёт. Мгновенный вебхук всегда найдёт свой платёж. Клиенту отдаётся `/api/pay/{payment}` — переход на страницу оплаты, который работает и во встроенном браузере Telegram на iOS.
3. Вебхук приходит на `/api/webhooks/pay/{провайдер}`. Провайдер проверяет подпись по сырому телу, и только после этого `inbox.handle` пишет вебхук в `webhook_inbox` (тело и безопасные заголовки). Затем одной транзакцией: блокировка платежа, сверка провайдера, транзакции и суммы с валютой, `payment → paid`, `order → paid`, `on_order_paid` модулей, задача `fulfill_order`, событие `payment_paid`. Если модуль отказал (например, поздняя оплата истёкшего счёта сверх лимита промокода), деньги принимаются, а заказ уходит на ручную проверку без задачи выдачи. Пополнение баланса зачисляется в журнал в той же транзакции.
4. Воркер берёт задачу. `fulfillment.run` выдаёт заказ на подписку под advisory-блокировкой подписки (`LockSpace::Subscription`; под ней же ручные дни, лимиты, блокировка доступа и действия с подпиской при возврате) и перечитывает заказ. Заказ ждёт другие заказы этой подписки, которые ещё в работе: оплаченные с сохранённым планом, оплаченные раньше него (кроме тех, у кого плана ещё нет и по платежу ждём возврат) и заказы на ручной проверке, у которых план применён или выдаётся после решения админа. План (`plan::plan`) с абсолютными значениями и исходным сроком `base_expire_at` сохраняется в заказ до первого вызова Remnawave. Срок в плане округляется вверх до целой секунды, со сроком Remnawave сравнивается с точностью до миллисекунды. После успешного запроса ставится `orders.plan_applied_at`, и повтор запрос не отправляет. Если перед повтором срок в Remnawave не равен ни исходному, ни целевому, заказ уходит на ручную проверку. Неприменённый план такого заказа помечается устаревшим (`orders.plan_stale_at`): он больше не применяется и не держит ни другие заказы подписки, ни автопродление. То же происходит, когда у задачи выдачи заказа на проверке кончились попытки. Дальше решает админ: «Пересчитать и выдать» или «Отметить выданным». Пока по платежу заказа ждём возврат (кроме возвратов повторных оплат), выдача откладывается; после отказа кассы или отмены заявки задача выдачи ставится снова. Заказ заблокированного клиента тоже уходит на проверку, пользователь в Remnawave не создаётся. Если клиента заблокировали во время выдачи, статус перепроверяется перед записью результата: пользователь Remnawave отключается, зеркало получает статус «отключена» (аудит `subscription.blocked_delivery`), уведомление о выдаче не уходит.
5. Выдача: `POST /api/users` или `PATCH /api/users`, при необходимости `reset-traffic`, затем свежий `GET` в зеркало и `order → fulfilled`. Повторное отключение и включение (ответы A029 и A030) считаются успехом. Имя нового пользователя — ник Telegram, без него часть почты до `@`, без неё `tg<Telegram ID>` или `id<номер клиента>` (`subscription::remna_name_base`, только латиница, цифры, `_` и `-`, до 36 символов); у второй подписки клиента `_2`, у третьей `_3`. Имя резервируется в `subscriptions.remna_username` при создании подписки. Если пользователь Remnawave с таким именем чужой (описание не `stealthnet client <uuid клиента>`) или имя занято другой подпиской, берётся следующий свободный номер; если имя заняли между расчётом плана и созданием, резерв меняется, план сбрасывается и выдача повторяется. Уже выданные подписки не переименовываются: Remnawave не умеет менять имя пользователя. При выключенных мультиподписках заказ на новую подписку — покупка клиента или выдача админом, — дошедший до выдачи, когда у клиента уже есть живая подписка (две оплаты или две выдачи до выдачи первой), привязывается к ней: покупка становится продлением или сменой, выдача админом остаётся выдачей и считается по категории (аудит `order.attached`).

Правила срока: продление (та же категория) — от `max(expireAt, дата оплаты)`, смена тарифа (другая категория или первая оплата после пробного) — от даты оплаты, оставшиеся дни не переносятся, трафик сбрасывается. Смена — это переход: подписка и пользователь Remnawave остаются те же (ссылка не меняется), сквады, лимиты и срок заменяются на новые. Бот, кабинет и мини-приложение перед оплатой пишут, что текущая подписка будет удалена, а новая станет доступна сразу.

Продление: при переходе с безлимита на лимит или при смене стратегии сброса счётчик трафика сбрасывается и ставится лимит тарифа; «Без сброса» прибавляет лимит, только если стратегия и до, и после — NO_RESET. Сквады, добавленные не тарифом, сохраняются: это текущие сквады минус сквады из снимка последнего выданного заказа. Если старый оплаченный срок ещё идёт, текущий лимит устройств держится до его конца (`subscription_device_holds`), потом обслуживание воркера снижает лимит до оплаченного в новом заказе и удаляет лишние устройства, начиная со старых. Смена тарифа и ручная правка доп. устройств снимают удержание.

Промокоды: живой резерв (заказ `pending`, срок резерва или счёта не истёк) занимает лимиты `max_uses` и `per_client`, поэтому второй счёт по одноразовому коду до оплаты, отмены или истечения первого получает отказ. Резерв берётся под блокировкой клиента и строки промокода, использование пишется при оплате в той же транзакции; при поздней оплате лимиты проверяются заново. Несуществующий и неподходящий код дают одинаковый ответ `promo.not_found`. Попытка засчитывается до проверки кода и прощается, если код подошёл; после 10 неудач клиента или 30 неудач с одного адреса за 15 минут — 429 `promo.rate_limited` (IPv6 считается по сети /64, внутренние адреса прокси не считаются, бот ограничен только по клиенту). Расчёт и оформление корзины с промокодом считают неудачи так же, но отвечают 422 `module.invalid`. Код неверного формата отклоняется без обращения к базе. Проверка и активация доводятся до конца, даже если клиент оборвал запрос.

Оплата с баланса — та же схема без провайдера: списание в журнал, платёж `paid` и задача выдачи в одной транзакции. Смешанной оплаты нет.

Повторная оплата уже оплаченного счёта с другой транзакцией провайдера — отдельный платёж `method = repeat`: сумма в валюте установки зачисляется на баланс, звёзды и другая валюта уходят на ручную проверку (`payment_repeats`, аудит `payment.repeat_credited` или `payment.repeat_review`, уведомление клиенту).

Возврат через платёжную систему без подтверждения (`completed = false`) записывается в `provider_refunds` как ожидающий: статус платежа и подписка не меняются, пока касса не подтвердит его вебхуком или опросом `fetch_refund` (задача `poll_payment` и обслуживание воркера). Отказ кассы (`RefundDeclined`) снимает ожидание. Сумма ожидающего возврата пополнения сразу удерживается записью `refund_hold`; отказ кассы или отмена возвращают её записью `refund_release`, подтверждение второго списания не делает. Действие с подпиской выполняется после подтверждения и при сбое повторяется из обслуживания воркера (пауза от минуты до часа, 12 попыток), затем аудит `subscription.refund_action_failed` и ручное решение. Опрашиваются только заявки систем с `supports_refund_polling`, по очереди времени последнего опроса. Ручной разбор — с правом «Возвраты»: `GET /api/admin/refunds/pending` — ожидающие заявки, `POST /api/admin/refunds/{id}/cancel` — отменить с пояснением (удержание возвращается), `POST /api/admin/refunds/{id}/confirm` — подтвердить вручную с пояснением, `GET /api/admin/refunds/actions` — несработавшие действия с подпиской, `POST /api/admin/refunds/{id}/action/retry` и `POST /api/admin/refunds/{id}/action/close` — повторить действие или закрыть с пояснением. Все действия пишутся в аудит.

Звёзды: счёт — `createInvoiceLink` с ценой в звёздах из тарифа. Бот получает `pre_checkout_query` и `successful_payment` и передаёт их в `inbox.stars_pre_checkout` и `inbox.stars_payment`; HTTP-вебхуков у звёзд нет. Оплаты и возвраты из пачки `getUpdates` сначала записываются в `bot_star_events`, и только потом бот сдвигает смещение. Непроведённые события бот повторяет сам (пауза от 30 с до 30 мин) и раз в минуту сверяет `getStarTransactions` от курсора `telegram.stars_offset.<id бота>`; расхождения уходят на ручную проверку (`payment.stars_review`). События на ручной проверке разбирает администратор с правом «Деньги»: `GET /api/admin/stars/review` — список, `POST /api/admin/stars/review/{id}/refund` — вернуть звёзды через `refundStarPayment` по списанию и плательщику (повтор безопасен), `POST /api/admin/stars/review/{id}/close` — закрыть с обязательным пояснением. Действия пишутся в аудит (`payment.stars_review_refunded`, `payment.stars_review_refund_failed`, `payment.stars_review_closed`). Уведомление Telegram о возврате списания, которое не проводилось как оплата, платежи не меняет.

## Очередь и периодические работы

- `jobs.dedupe_key` уникален только среди задач `queued` и `running`: выполненную или ушедшую на проверку задачу можно поставить снова (`ensure_queued`).
- Воркер берёт задачи по одной с токеном аренды и продлевает аренду каждую треть её срока. Итог записывает только владелец аренды.
- Обслуживание, раз в минуту: отмена просроченных счетов, чистка `webhook_inbox`, опрос ожидающих возвратов и повтор действий с подпиской после возврата, снятие удержанных доп. устройств.
- Досверка выдачи, раз в 5 минут: заказ `paid`, оплаченный больше 2 минут назад, без активной задачи, у которого последняя задача затихла больше 30 минут, ставится в очередь снова (аудит `order.redeliver`). Заказ с ожидающим возвратом досверка не берёт. Заказ на ручной проверке решает админ (право «Деньги»): список `GET /api/admin/orders/review`, «Повторить выдачу» `POST /api/admin/orders/{id}/redeliver`, «Пересчитать и выдать» `POST /api/admin/orders/{id}/recalculate`, «Отметить выданным» `POST /api/admin/orders/{id}/mark-fulfilled`. Каждое действие пишется в аудит заказа.
- Автопродление выбирает подписки в SQL постранично: незавершённые, с включённым автопродлением, в окне списания и повторов. Списание с карты держит платёж до конца окна повторов плюс день, а задачу `poll_payment` ставит в одной транзакции с платежом до запроса к кассе. Неизвестный исход уточняется статусом по номеру платежа или повтором запроса с тем же ключом идемпотентности в течение 20 часов. Повтор уходит, только пока продление ещё нужно: клиент не заблокирован, автопродление включено, подписка не завершена и не отключена, её срок равен циклу попытки, нет другого оплаченного и не выданного заказа подписки. Иначе новый запрос не отправляется, платёж ждёт ручной проверки (аудит `payment.autorenew_unclear`). Блокировка клиента не отменяет автосписание с невыясненным исходом: подтверждённая оплата уходит на ручную проверку (аудит `payment.autorenew_blocked`), отказ кассы отменяет платёж и заказ, разблокировка возобновляет опрос. Заказ на ручной проверке держит автопродление, только если его план применён или выдаётся либо заказ оплачен самим автопродлением.
- Раз в час подписка, истёкшая больше `max(90, retry_days + 8)` дней назад и без открытых заказов, получает `ended_at`, если это не откроет клиенту пробный период. Покупка такой подписки снимает `ended_at`.

## Связь с Remnawave

- Клиент: таймаут 12 с, без редиректов, `Bearer`-токен, необязательная кука защиты, для `http://` внутри docker-сети — заголовки `X-Forwarded-For` и `X-Forwarded-Proto: https`, без них панель рвёт соединение.
- Ошибки: `NotFound` — пользователя нет; `Timeout`, 5xx и обрыв — исход неизвестен (`outcome_unknown`), перед повтором нужна сверка; 400 с кодом `A0xx` — отказ панели.
- Подключение (адрес, токен, кука, секрет вебхуков) хранится в настройках и зашифрованных секретах; переменные окружения — запасной вариант для первого запуска. `Services::reload` пересоздаёт клиента без перезапуска.
- Вебхуки: `POST /api/remnawave/webhook`, подпись `X-Remnawave-Signature` = HMAC-SHA256 сырого тела секретом `WEBHOOK_SECRET_HEADER`. Повтор отсекается по SHA-256 тела. В базу пишется тело без `vlessUuid`, паролей и ссылки подписки. Обработка — задачей `process_remna_event`: зеркало обновляется, только если `updatedAt` из события не старше сохранённого.
- Вебхук — быстрый сигнал, а не истина: события теряются, если сервис лежал дольше 15 секунд. Сверка `remna_sync.reconcile` по `stale_mirrors` обязательна.
- Массовые операции — только `bulk/*` по спискам до 500 id, `bulk/all/*` не используем.

## Валюта и звёзды

- Валюта установки — настройка `core.currency`. Цены периодов и доп. устройств хранятся по валютам (`price_usd_minor`, `price_rub_minor`), видна только цена валюты установки; периоды без неё не продаются.
- Скидки: в долларах — до цента, в рублях — до целого рубля (на экранах рубли без копеек). Проценты округляются половиной вверх.
- Звёзды — отдельная цена у срока и у доп. устройства. Процентная скидка в звёздах округляется до целой звезды, фиксированная к звёздам не применяется. Пополнять баланс звёздами нельзя.
- Баланс ведётся журналом `balance_entries`; остаток в `client_balances` с `CHECK (amount_minor >= 0)` меняется в той же транзакции. Реферальные начисления — отдельный кошелёк, вывод только из него.

## Безопасность входящих запросов

- Платёжные вебхуки: подпись проверяет провайдер по сырым байтам и в постоянное время. Платёж сверяется по провайдеру, транзакции, сумме и валюте; недоплата не засчитывается никогда. Ответ 2xx — только когда событие записано и обработано или сознательно пропущено; при внутренней ошибке — 503, чтобы провайдер повторил. Повтор тела с неверной подписью не мешает настоящему уведомлению. Повтор уже обработанного вебхука получает ответ в формате провайдера.
- Неизвестная платёжная система получает 404, тело больше 64 КиБ — 413, оба ответа до записи в базу. Уведомления принимает любая настроенная система, даже выключенная: `enabled` влияет только на показ способа и новые счета. Ненастроенная система получает 404, отказ пишется без тела (`not_accepted`). Тело сохраняется только после проверки подписи. Отказы пишутся без тела, не больше 30 записей с одного адреса за 10 минут (IPv6 — по /64). Принятые записи и подлинные уведомления, отклонённые проверкой (`rejected_business`), хранятся 30 дней; отказы по подписи и записи без тела — 3 дня. Для систем, которые проверяют подлинность запросом к своему API (ЮKassa), с одного адреса проходит не больше 10 непроверенных уведомлений в минуту, дальше 429; ненайденный идентификатор помнится 60 секунд.
- `accepts_http_webhooks = false` у баланса и звёзд: их нельзя «оплатить» HTTP-запросом.
- Провайдер, который ещё не реализован или не проверяет подлинность (Overpay), считается ненастроенным и клиентам не предлагается.
- Мини-приложение: `initData` проверяется по HMAC от токена бота, повтор ключей отклоняется, срок жизни — час. Токен приходит в теле ответа и передаётся только в `Authorization: Bearer`: куку мини-приложению не ставим, его сессии по куке не принимаются.
- Изменяющие запросы (POST, PUT, PATCH, DELETE), авторизованные кукой клиента или админа, принимаются только со своего сайта: `Origin` из `SN_PUBLIC_URL`, адреса в настройках или `SN_CORS_ORIGINS`, либо `Sec-Fetch-Site: same-origin` или `none`, а без `Sec-Fetch-Site` — `Origin`, совпадающий с `Host`. Иначе 403 `auth.cross_site`. Запросы с `Bearer` и запросы без `Origin` и `Sec-Fetch-Site` эта проверка не касается.
- Вход админа: лимиты считают только неудачи пароля — 10 за 15 минут на пару почта и адрес и 20 за 15 минут на почту; с одного адреса — 30 любых попыток за 5 минут. Общий лимит на почту не действует на адрес, с которого этот админ успешно входил за последние 30 дней (`admin_login_addresses`): перебор с чужих адресов не закрывает вход с привычного. Во всех лимитах по адресу IPv6 считается по сети /64. Неверный код TOTP после верного пароля: 5 за 15 минут и 20 за сутки на админа, дальше 429 и аудит `admin.totp_locked`.
- Сессии админов и клиентов — случайные токены, в базе только SHA-256. Пароли — argon2id, старые bcrypt-хеши принимаются при входе.
- Администраторы (право `admins`, по умолчанию только у владельца): `GET/POST /api/admin/admins`, `POST /api/admin/admins/{id}/role|disable|enable|password|2fa/reset`. Новому администратору и при сбросе пароль придумывает сервер (16 знаков без похожих символов) и отдаёт один раз; у такого админа `must_change_password`, и админка не пускает дальше экрана смены пароля. Себя менять нельзя (`admins.self`), владельцами распоряжается только владелец (`admins.owner_only`), последнего действующего владельца нельзя понизить или отключить (`admins.last_owner`, проверка под `FOR UPDATE` по владельцам). Отключение и сбросы закрывают все сессии этого админа; сессии отключённого не принимаются уже на поиске токена. Каждое действие пишется в аудит (`admin.created`, `admin.role_changed`, `admin.disabled`, `admin.enabled`, `admin.password_reset`, `admin.totp_reset`). Свой пароль и вход по коду админ меняет на странице «Безопасность» (`/auth/password`, `/auth/2fa/*`).
- API-ключи (право `settings`): `GET/POST /api/admin/api-keys`, `POST /api/admin/api-keys/{id}/revoke`. Токен `snk_…` из 24 случайных байт показывается один раз, в базе только SHA-256 и первые 12 знаков для списка. Ключ передаётся как `Authorization: Bearer`, кукой не принимается. Права ключа выбираются при создании и не шире прав создателя; при каждом запросе они ещё раз пересекаются с текущими правами создателя, а у отключённого создателя ключ не работает. Ключ не получает права `admins`, не управляет ключами и не трогает `/auth/password`, `/auth/security`, `/auth/2fa/*`. Срок — по часам сервиса, «последнее использование» обновляется не чаще раза в минуту. Создание и отзыв пишутся в аудит (`api_key.created`, `api_key.revoked`).
- Почта: модуль `mail` хранит подключение SMTP (сервер, шифрование STARTTLS/TLS/без, порт, логин, пароль — секретом, адрес и имя отправителя) и проверяет его при сохранении; отправляет письма сервис `mail` ядра через `lettre` (rustls), таймаут 20 с, ошибка сервера возвращается текстом без секретов. Вход в кабинет по почте шлёт код письмом (15 минут); пока почта выключена или не заполнена, `POST /api/client/auth/email` отвечает 501, а `/api/public/site` отдаёт `email_login: false`, и кабинет прячет вкладку «Почта». Проверочное письмо — `POST /api/admin/mail/test` (право `settings`, только из сессии). Раздел «Настройки → Почта и уведомления».
- Секреты в базе зашифрованы AES-256-GCM ключом `SN_SECRET_KEY`, имя настройки участвует в шифровании, поэтому секрет нельзя подменить другим.
- Реальный IP клиента берётся из `X-Forwarded-For` только от доверенных прокси: цепочка разбирается справа до первого недоверенного адреса. Пустой `SN_TRUSTED_PROXIES` означает loopback и шлюз Docker (внутри контейнера), явный список адресов и сетей CIDR заменяет умолчания. Если первые 20 запросов пришли от доверенного прокси без `X-Forwarded-For`, в журнал один раз пишется предупреждение, что прокси не передаёт адрес клиента.

## Хранилище

- Ключи `bigint identity`, наружу — `public_id uuid`. Время — `timestamptz`, соединения работают в UTC. Перечисления — `text` с `CHECK`, без типов `enum` в PostgreSQL. Снимки цены, тарифа и плана — `jsonb` в заказе.
- Миграции — `crates/sn-store/migrations`, применяются `sqlx` (`stealthnet migrate` или при `serve`) с контрольными суммами. Выпущенную миграцию не правим, только добавляем новую.
- Идемпотентность: `UNIQUE` на `(provider, provider_txid)`, `balance_entries.idempotency_key`, `jobs.dedupe_key` (среди активных задач), `remna_events.body_sha256`, `webhook_inbox (source, dedupe_key)`, `bot_star_events (charge_id, event)`, `event_deliveries (event_id, module)`.

## Переход со старой версии 7.x

Перенос — отдельная команда (`stealthnet import-legacy`, будет написана), которая читает старую базу Prisma и пишет в новую. План:

1. Валюта установки. Определить по настройке и фактическим оплатам. Если в старой базе оплаты в двух валютах, клиентов со смешанным балансом не пересчитывать курсом, а выгрузить владельцу на ручное решение.
2. Клиенты. `clients` + `client_identities` (Telegram, почта, Google, Apple), пароли bcrypt как есть, TOTP-секреты зашифровать. Старые `cuid` — в `legacy_ids`. Модульные поля (рефералы, UTM, личная скидка) — в таблицы модулей.
3. Баланс. Одна запись `migration_opening` на клиента в валюте установки, `Float` → минорные единицы с округлением до копейки.
4. Тарифы. Категории, тарифы, сквады; `TariffPriceOption` → `tariff_periods` с ценой в валюте тарифа; цены в звёздах оператор задаёт сам. `on_purchase` → «при каждой оплате», `monthly` → MONTH, `monthly_rolling` → MONTH_ROLLING, `carry_over` — по решению владельца.
5. Подписки. `remna_user_id` — число; UUID из 2.x разрешить алгоритмом `migrate-remna-ids.ts` (shortUuid → Telegram ID или почта → срок), неоднозначные — в отчёт. После переноса каждую подписку перечитать из Remnawave.
6. Платежи — история: тип по старой эвристике и `metadata`, суммы в минорных единицах, звёзды как XTR, исходный `metadata` — в архив. Незавершённые выдачи (`PaymentDelivery` в PENDING и REVIEW) — в ручную проверку. Курсор сверки звёзд `telegram_stars_offset_<botId>` — в `bot_state` под ключом `telegram.stars_offset.<id бота>`, иначе первая сверка перечитает всю историю звёзд.
7. Поддержка, согласия с документами, администраторы, шаблоны уведомлений — перенести; журналы вебхуков, рассылок, рулетки, маркетплейса — в архивный дамп.
8. Сверки после переноса: сумма балансов, число и сумма оплат по месяцам и провайдерам, у каждой подписки свой пользователь Remnawave и наоборот, вход по почте, Telegram и мини-приложению.

## Что работает и чего ещё нет

Работает и покрыто тестами:

- Покупка: расчёт цены со скидками модулей, счёт у платёжной системы или оплата с баланса, пополнение баланса, пробный период.
- Платёжные системы: Crypto Pay, Heleket, Lava.top, ЮKassa, Platega, ЮMoney, CloudPayments, звёзды Telegram и баланс. Вебхуки, опрос счёта, повторные оплаты, возвраты на баланс и через кассу, ожидающие возвраты.
- Выдача в Remnawave: новая подписка, продление, смена тарифа, пробный период; повторы, досверка и ручной разбор заказов.
- Подписки: дни и лимиты вручную, сброс трафика, устройства, перевыпуск ссылки, блокировка и разблокировка клиента, автопродление с баланса и сохранённой карты, завершение давно истёкших.
- Связь с Remnawave: вебхуки, зеркало, сверка, ноды и сквады.
- Вход: админ с паролем и TOTP, мини-приложение, вход на сайт через бота.
- API админки: главная и лента, клиенты, платежи и возвраты, заказы, заявки на возврат и оплаты звёздами на ручной проверке, тарифы и категории, настройки, платёжные системы, модули, поддержка. Главная показывает счётчики ручной работы: `orders_review`, `stars_review`, `refund_actions_failed`.
- API кабинета и мини-приложения: каталог, расчёт, оформление, пополнение, подписки, устройства, автопродление, поддержка.
- Бот: покупка, оплата звёздами, вход на сайт, уведомления.
- Модули: промокоды, рефералы, UTM-метки, доп. опции. Остальные 19 из каталога — заглушки.

Ещё не написано:

- Вход по почте: `POST /api/client/auth/email` отвечает `not_implemented` (501), пока нет модуля «Почта».
- Overpay: провайдер-заглушка, считается ненастроенным и клиентам не предлагается.
- Покупка доп. устройств в середине срока: оплата принимается и записывается, но лимит устройств ядро не меняет, заказ уходит на ручную проверку.
- Ручная правка доп. устройств у подписки без оплаченного периода отвечает `not_implemented`.
- Выдача подписки админом без оплаты: план выдачи это умеет, но сценария и маршрута, которые создают такой заказ, нет.
- Управление администраторами через API: роли и права проверяются, но завести сотрудника можно только в базе; владельца создаёт `create-admin`.
- `stealthnet import-legacy`: команда есть, перенос не написан.
- Сообщения администраторам о ручной работе: есть счётчики на главной и списки, уведомлений в Telegram нет.
- Интерфейсов админки, кабинета и мини-приложения в репозитории нет.
