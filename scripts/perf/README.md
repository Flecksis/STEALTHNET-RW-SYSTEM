# Замер скорости на большой базе

Синтетическая база размером с крупного оператора: 300 тыс. клиентов, около миллиона заказов и 1,5 млн платежей, 270 тыс. подписок, 100 тыс. обращений, миллионы строк в журналах. Реальные данные не нужны: всё строится генератором, повторный запуск даёт ту же базу.

## База

```bash
createdb -h 127.0.0.1 -p 55432 -U postgres sn_perf
DATABASE_URL=postgresql://postgres@127.0.0.1:55432/sn_perf stealthnet migrate
DATABASE_URL=postgresql://postgres@127.0.0.1:55432/sn_perf SN_ADMIN_PASSWORD=<пароль> stealthnet create-admin --email perf@example.test
psql -h 127.0.0.1 -p 55432 -U postgres -d sn_perf -v scale=1 -f scripts/perf/seed.sql
psql -h 127.0.0.1 -p 55432 -U postgres -d sn_perf -c "VACUUM (ANALYZE)"
```

`scale` меняет объём: `0.01` — 3 тыс. клиентов для проверки генератора, `1` — полный объём, около 6 ГБ и 5 минут. Генератор работает только на пустой базе после миграций и пишет пачками по 50 тыс. строк.

Миграция 0290 (маскирование тел уведомлений платёжек) отмечается применённой за 90 дней до данных: поиск в журнале уведомлений смотрит в тела только после неё, и без этой отметки замер не увидел бы поиска по телам, как на живой панели.

## Замер API

Панель запускается на этой базе без воркера и бота (`SN_RUN_WORKER=false SN_RUN_BOT=false`), затем:

```bash
PERF_EMAIL=perf@example.test PERF_PASSWORD=<пароль> python3 scripts/perf/bench.py --runs 15 --out bench.json
```

Скрипт входит в админку, берёт из базы образцы (обычный и самый тяжёлый клиент, обращение, платёж), проходит по экранам админки, кабинета и мини-приложения и печатает p50 и p95 в миллисекундах. `--only <слово>` оставляет часть замеров, `--part admin|client` — одну сторону.

## Бот

`scripts/perf/bot_bench.py` поднимает подставной Bot API на 18125 и отправляет боту `/start` и нажатия кнопок покупки. Панель запускается с `SN_RUN_BOT=true`, `TELEGRAM_BOT_TOKEN=123456:perf` и `SN_TELEGRAM_API=http://127.0.0.1:18125`.

## Постоянная нагрузка и запросы на действие

`scripts/perf/load.py` поднимает подставной Bot API на `--tg-port` и работает в трёх режимах. Панель запускается с `SN_RUN_BOT=true`, `TELEGRAM_BOT_TOKEN=123456:perf`, `SN_TELEGRAM_API=http://127.0.0.1:<tg-port>`, адресом Remnawave-заглушки в `REMNAWAVE_URL` и `SN_TRUSTED_PROXIES=127.0.0.1`: у каждого виртуального клиента свой адрес в `X-Forwarded-For`, иначе ограничение попыток входа с одного адреса исказит замер.

```bash
python3 scripts/perf/load.py run --base http://127.0.0.1:18470 --dsn <база> --remna http://127.0.0.1:18472 \
  --tg-port 18471 --bot-token 123456:perf --bot-users 150 --web-users 60 --admins 2 \
  --email <почта> --password <пароль> --duration 90
```

- `run` — постоянная нагрузка: чаты бота проходят `/start`, меню, «Мои подписки», «Моя подписка», покупку до счёта звёздами; клиенты кабинета и мини-приложения (с входом по `initData`) открывают свои экраны; администраторы обходят главную, клиентов, карточку, платежи и журнал. В конце — p50, p95, p99 и число запросов к Remnawave (заглушка отдаёт счётчики на `/__stats`).
- `count` — по одному действию бота, кабинета, мини-приложения и админки и число запросов к базе и Remnawave на каждое. Панель запускается с `SN_LOG=info,sqlx::query=debug` и `SN_LOG_FORMAT=json`, журнал передаётся в `--log`.
- `jobs` — раз в полсекунды ставит в очередь уведомление и меряет, сколько оно ждёт выполнения, пока воркер занят периодическими работами (панель с `SN_RUN_WORKER=true`).
- `broadcast` — создаёт и запускает рассылку (`--audience`, картинка `--photo`) через админку, пока чаты бота (`--bot-users`) нажимают кнопки; `--tg-limit 30` заставляет подставной Bot API отвечать 429 сверх 30 отправок за секунду. В отчёте — темп рассылки по секундам, самая плотная секунда, число 429, загрузки картинки и отправки по `file_id`, паузы между отправками, процессор и память панели (`--pid`) и время ответов бота без рассылки и во время неё. Панель — с ботом и воркером, `--settle` даёт воркеру закончить работы после запуска.

Заглушка Remnawave должна отдавать пользователей подписок этой базы (номер, имя, `shortUuid`, срок и трафик из `subscriptions`), `GET /api/users/stream` и счётчики вызовов.

## Миграции

`scripts/perf/locks.sql` повторяет на большой базе приёмы прошлых миграций в транзакциях с откатом и показывает, сколько каждый держит блокировку.
